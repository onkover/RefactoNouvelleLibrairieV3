1. Rappel — d’où l’on part

Ce lot est le premier de LibraryV3 : aucun lot ne le précède. Ce qui le précède, c’est LibV2, l’ancien moteur, dont l’audit a conduit à repartir de zéro. Sur le terrain de cette leçon, l’audit relevait notamment :

Constat dans LibV2Conséquence
enum { _LEFT, _NEAR, _FAR } (bug B11)Identifiants réservés au compilateur, et collision avec les macros NEAR/FAR de windows.h : comportement indéfini.
Trois énumérations pour un seul concept : PointVSPlane, FrustumInside, PlaneSideAucun vocabulaire commun : chaque fichier réinvente le sien, et les conversions entre eux sont silencieuses.
Frustum.h incluait Camera.h, Mesh.h et GfxFunctions.hCouches inversées : un header mathématique dépendait du rendu. Toute retouche se propageait partout.

Leçon tirée : avant d’écrire la moindre ligne de rendu, il faut décider où vit chaque déclaration. C’est l’objet de ce lot.

2. Contexte — le projet

LibraryV3 est une bibliothèque statique (projet LIB) utilisée par un exécutable séparé (RefactoNouvelleLibrairieV3, projet EXE), sous Visual Studio 2026 en C++23. Trois faits du projet cadrent toute la leçon :

Le header précompilépch.cpp est compilé avec /Yc"pch.h" : il produit le fichier précompilé. Tous les autres .cpp sont compilés avec /Yu"pch.h" et commencent par #include "pch.h". Le compilateur relit alors le résultat précompilé au lieu de réanalyser la STL à chaque fichier.
Deux projets, mêmes headersLa LIB et l’EXE incluent les mêmes en-têtes publics. Une constante ou un type doit donc avoir une seule définition, au même endroit, vue identiquement par les deux projets.
Trois moments où une valeur peut changerJamais (π), entre deux compilations (un plafond de lumières), entre deux exécutions (la taille de la fenêtre). La leçon donne un foyer à chacun.

3. Objectif fonctionnel du lot et son intérêt

À la fin de ce lot, le moteur dispose d’une infrastructure de headers sur laquelle tout le reste se construit :

Un vocabulaire communLes énumérations partagées (EAxis, ESpace, EFace…) existent une seule fois, avec une taille garantie, visibles partout.
Une compilation qui coûte ce qu’elle doitRetoucher un réglage ne recompile que les fichiers concernés ; seul un changement de constante absolue reconstruit tout.
Aucune collision de macroswindows.h reste confiné ; std::min, near et far gardent leur sens dans tout le moteur.
Des réglages sans recompilerCe qui varie d’une exécution à l’autre se lit dans config.json.
Des inclusions lisiblesUn #include dit d’où vient le fichier : guillemets pour le dépôt, chevrons pour le reste.

Intérêt. Ces décisions sont invisibles à l’écran, mais elles se paient à chaque compilation et à chaque bug de collision. Prises maintenant, elles coûtent une leçon ; prises après coup, elles imposent de reprendre les inclusions de tout le moteur.

4. Décisions à prendre et leur pourquoi

Chaque décision est dictatoriale : tranchée une fois, elle ne se rouvre pas à la légère. Cliquez pour voir la question, la décision, sa justification et l’alternative écartée.

D1
Ce qui a le droit d’entrer dans pch.h
Critère : stable ET sans pollution

Question. Le PCH accélère la compilation, mais tout ce qu’il contient devient une dépendance de chaque .cpp. Qu’y met-on ?

Décision. Un header entre dans pch.h seulement s’il remplit deux conditions à la fois : son contenu ne changera plus, et il n’injecte aucune macro dans le scope global. En pratique : la STL, Compiler.h, config.h, CoreTypes.h.

Pourquoi. Le PCH est reconstruit dès qu’un de ses headers change, et avec lui tous les .cpp compilés en /Yu. Un header instable dans le PCH transforme chaque petite retouche en build complet ; un header pollueur y contamine chaque fichier du projet.

Alternative écartée. Tout mettre dans le PCH « pour gagner du temps ». Le temps gagné au premier build est reperdu à chaque modification, et le moindre réglage recompile le moteur entier.
D2
Trois étages de configuration
config.h · EngineSettings.h · config.json

Question. Une valeur du moteur (π, nombre maximal de lumières, largeur d’écran) : où la déclarer ?

Décision. Trois étages, selon la fréquence de changement. Constante absolue → config.h (dans le PCH). Réglage de compilation qui se retouche → EngineSettings.h (hors PCH). Paramètre qui varie d’une exécution à l’autre → config.json, lu au démarrage par EngineConfig.

Pourquoi. Chaque étage a un coût de modification différent : rebuild complet, recompilation de quelques .cpp, ou aucune recompilation. Ranger une valeur au bon étage, c’est payer le coût juste quand on la change.

Alternative écartée. Un fichier unique de constantes. Changer la résolution d’écran obligerait alors à recompiler, et changer un réglage de tuning reconstruirait le PCH.
D3
windows.h isolé dans Platform.h
Inclus par le seul .cpp qui en a besoin

Question. Le moteur a besoin, ponctuellement, de l’API Windows. Comment l’inclure sans contaminer le reste ?

Décision. windows.h n’est inclus que dans Core/Platform.h, et Platform.h uniquement dans les .cpp qui appellent l’API OS. Jamais dans le PCH, jamais dans un .h public.

Pourquoi. windows.h définit des macros comme min, max, near, far, NEAR, FAR. Des macros n’ont pas de namespace : elles réécrivent le texte de tout fichier qui les voit, y compris std::min ou une variable near de caméra. NOMINMAX retire min/max, pas near/far.

Alternative écartée. #include <windows.h> dans le PCH « parce que c’est pratique ». Le bug B11 de LibV2 (_NEAR, _FAR) est exactement ce genre de collision.
D4
Toujours enum class, toujours un type sous-jacent
enum class E : uint8_t { … }

Question. Comment déclarer une énumération du moteur ?

Décision. Uniquement enum class, avec un type sous-jacent explicite (: uint8_t, : uint32_t). Accès qualifié : ELightType::Point.

Pourquoi. enum class confine les noms des valeurs dans le type (pas de Point qui entre en collision avec un autre Point) et interdit les conversions implicites vers int. Le type sous-jacent fixe la taille : elle devient garantie dans les structures et stable dans les fichiers de scène.

Alternative écartée. L’enum nu de LibV2 (FrustumInside { INSIDE, OUTSIDE, INTERSECT }) : valeurs dans le scope global, taille laissée au compilateur (4 octets sur MSVC), conversions implicites silencieuses.
D5
Le filtre de CoreTypes.h
Liste close ET au moins deux systèmes

Question. Une énumération partagée : dans CoreTypes.h (PCH) ou dans le header de son système ?

Décision. Elle entre dans CoreTypes.h seulement si sa liste de valeurs est close et si au moins deux systèmes distincts l’utilisent (EAxis, ESpace, EFace, EWindingOrder, EEnabled). Sinon, elle va dans le header de son système (RenderTypes.h, LightTypes.h, SceneTypes.h).

Pourquoi. Une liste ouverte change au fil des fonctionnalités : dans le PCH, chaque nouvelle valeur provoquerait un rebuild complet. Une énumération propre à un système n’a pas à être vue par tout le projet.

Alternative écartée. Un seul header « tous les enums du moteur ». Ajouter un mode de rendu recompilerait la physique, et LibV2 a fini avec trois énumérations pour un seul concept (PointVSPlane, FrustumInside, PlaneSide).
D6
ELayerMask : un bitmask de 32 bits
uint32_t + opérateurs |, &, ~

Question. Les couches de rendu se combinent (« Default et Physics ») : comment les représenter ?

Décision. enum class ELayerMask : uint32_t, une valeur par bit, et les opérateurs |, &, ~ surchargés explicitement, plus HasLayer().

Pourquoi. 32 bits donnent 32 couches, comme Unity. Le type est choisi une fois pour toutes : il fait partie du format des scènes sauvegardées. Les opérateurs sont nécessaires parce qu’enum class les interdit par défaut, et c’est voulu : on ne les ouvre que pour ce type.

Alternative écartée. uint8_t « pour économiser » : 8 couches seulement, et passer plus tard à 32 bits casserait la lecture des scènes déjà écrites.
D7
#if plutôt que #ifdef pour les options
Désactiver = mettre à 0

Question. Comment activer ou désactiver une fonctionnalité à la compilation ?

Décision. Chaque option est toujours définie, à 0 ou 1, et testée par #if.

Pourquoi. Avec #ifdef, une option mise à 0 reste « définie » et sa branche est compilée quand même ; il faudrait supprimer le #define, ce qui laisse des références orphelines. Avec #if, la valeur décide, et le symbole existe toujours.

Alternative écartée. #ifdef LV3_FEATURE_SHADOWS : écrire #define LV3_FEATURE_SHADOWS 0 ne désactive rien.
D8
Guillemets ou chevrons : la forme d’un #include
"…" pour le dépôt · <…> pour le reste

Question. Un #include accepte deux formes. Laquelle écrire, et pourquoi la forme compte-t-elle si les deux compilent ?

Décision. Guillemets pour tout fichier qui appartient au dépôt (LIB ou EXE, y compris une bibliothèque tierce copiée dans le projet, comme json.hpp). Chevrons pour la STL, le SDK Windows et toute dépendance installée hors du dépôt (SDL2). Les chemins du dépôt s’écrivent depuis la racine de la LIB ("Core/Platform.h"), et "pch.h" reste la première ligne de chaque .cpp.

Pourquoi. Pour MSVC, les deux formes finissent par parcourir les mêmes dossiers : les /I, puis la variable INCLUDE. Seul le point de départ change. La forme à guillemets commence par le dossier du fichier qui contient la directive, puis remonte la chaîne des fichiers qui l’ont inclus ; la forme à chevrons commence directement par les /I. Deux conséquences : un fichier du dépôt inclus avec des guillemets est trouvé près de son voisin avant tout autre candidat de même nom, et un include à chevrons ne peut jamais être détourné par un fichier local. La forme porte donc une information vérifiable, pas une préférence de style.

Alternative écartée. Chevrons partout « parce que ça compile ». Ça compile tant que les /I du projet sont ceux qu’on croit. Le jour où deux fichiers portent le même nom (config.h est un nom très courant), c’est le premier dossier de la liste /I qui gagne, en silence : voir CE5.
D9
Une seule extension : .h
Décision proposée, à confirmer

Question. .h ou .hpp pour les headers du moteur ?

Décision proposée. .h pour tous les headers du moteur, comme dans le dépôt aujourd’hui (Compiler.h, config.h, CoreTypes.h, Platform.h, MathTypes.h, Transform.h…). .hpp n’apparaît que sur la bibliothèque tierce embarquée, json.hpp.

Pourquoi. Le compilateur ne regarde pas l’extension : MSVC, GCC et Clang traitent .h et .hpp de la même façon, et Visual Studio les range dans le même filtre « Fichiers d’en-tête ». La convention « .h = C ou C++, .hpp = C++ seul » n’informe le lecteur que si le projet mélange du C et du C++. LibraryV3 ne contient aucun fichier C. Le critère retenu est donc la constance : une seule extension, pour que personne n’ait à se rappeler laquelle un fichier porte.

Alternative écartée. .hpp pour tout le C++ pur : convention répandue et défendable. Elle imposerait de renommer des headers déjà inclus partout, sans gain technique. La leçon 02 l’emploie dans sa liste de fichiers, alors que le dépôt ne l’a jamais suivie : voir E13.

E1config.h — les constantes deviennent des constexprÉvolution à retenir + dette mineure
Leçon d’origine
#define LV3_PI 3.14159…, #define LV3_EPSILON 1e-6f.
Dépôt actuel
constexpr dans namespace LV3 : M_PI, M_PI_2, TO_RADIAN, INV_PI… Commentaire du fichier : « pour éviter d’inclure <corecrt_math_defines.h> ».
Raison de l’écart
Disposer des constantes mathématiques usuelles sans activer _USE_MATH_DEFINES, qui ne s’obtient qu’en les déclarant comme macros globales.
Ce qu’il apporte
Une constexpr a un type (double ou float, choisi), un scope (LV3::), une adresse visible dans le débogueur, et ne réécrit aucun texte. C’est strictement mieux qu’un #define, et cohérent avec la règle D3 : moins de macros globales.
Verdict
À retenir : les constantes du moteur sont des constexpr dans LV3, plus des macros. Dette mineure : les noms M_PI, M_E… sont exactement ceux des macros de <cmath>. Si un fichier définit un jour _USE_MATH_DEFINES, la macro réécrit constexpr auto M_PI = … en constexpr auto 3.14159… = … et la compilation casse sur une ligne correcte. Renommer (kPi, kHalfPi…) éteint le piège.
E2config.h — une tolérance n’est pas une garde anti-divisionÉvolution à retenir
Leçon d’origine
Une seule constante, LV3_EPSILON = 1e-6f, pour tout : comparer deux floats et éviter une division par zéro.
Dépôt actuel
Deux familles séparées : des tolérances (EPSILON = 0.01f grossière, EPSILON_FLOAT = 0.001f fine) et des gardes anti-division (NEAR_ZERO = 1e-15f, NEAR_ZERO_SQ = 1e-30f), avec le commentaire « ce n’est PAS une tolérance ».
Raison de l’écart
Bug n°3 de la leçon 05 : la normalisation d’un plan du frustum était gardée par EPSILON_FLOAT = 1e-3, alors que la normale du plan far valait 1e-4. La garde rejetait une longueur parfaitement valide : plan jamais normalisé, culling faux.
Ce qu’il apporte
Une tolérance répond à « ces deux valeurs sont-elles égales à l’échelle de la scène ? ». Une garde répond à « ce dénominateur est-il nul ? ». Leurs ordres de grandeur n’ont rien à voir ; deux noms distincts empêchent de prendre l’une pour l’autre.
Verdict
À retenir : règle de nommage permanente, une garde anti-division s’écrit avec NEAR_ZERO*, jamais avec EPSILON*. Point de vigilance : EPSILON = 0.01f est une tolérance absolue, valable à l’échelle des scènes actuelles ; elle ne s’adapte pas seule à une scène en kilomètres ou en millimètres.
E3config.h — LV3_ASSERT ne passe plus par assertÉvolution à retenir
Leçon d’origine
#define LV3_ASSERT(x) assert(x) sous _DEBUG, ((void)0) sinon.
Dépôt actuel
LV3_ASSERT(...) appelle LV3::AssertFailed (message, __debugbreak, abort) quand LV3_ASSERTS_ENABLED vaut 1 ; sinon ((void)sizeof(!(…))). Annexe A10, §8.3.
Raison de l’écart
La configuration RelWithAsserts (mesurer en Release sans retirer les filets) ne fonctionnait pas : Release définit NDEBUG, qui neutralise assert. Le commutateur ne commutait rien.
Ce qu’il apporte
Les invariants restent actifs là où on les demande, Release compris. Le sizeof fait compiler l’expression même éteinte : un assert qui référence un membre supprimé casse le build au lieu de pourrir en silence. Première compilation : FragmentContext::magic trouvé incohérent. __VA_ARGS__ accepte une virgule dans l’expression.
Verdict
À retenir : règles R45 à R47 (tests et invariants sur des commutateurs distincts, assert sans effet de bord, témoin et contrôle sous le même commutateur).
E4config.h — les commutateurs de build vivent dans le PCHÉvolution à retenir
Leçon d’origine
Les options (LV3_FEATURE_*) vivent dans EngineSettings.h, hors PCH (décisions D1 et D2).
Dépôt actuel
Une douzaine de commutateurs dans config.h (asserts, journaux, mesure, ablations, variantes de rendu), chacun sous #ifndef, testé par #if, borné par des #error de cohérence. Certains reçoivent leur valeur de LV3.Common.props.
Raison de l’écart
Bug 0.3 : LV3_ASSERTS_ENABLED était défini côté EXE seulement. Un header partagé (FrameBuffer.h, DepthBuffer.h) était alors compilé sous deux formes dans un seul binaire, une quasi-violation de l’ODR (règle R38). Ces commutateurs doivent avoir une seule valeur, vue par toutes les unités de traduction des deux projets.
Ce qu’il apporte
La nuance qui manquait à D1 : le PCH se paie quand un réglage consommé par quelques fichiers recompile tout. Un commutateur qui change le code de tous les fichiers doit tout recompiler de toute façon ; le sortir du PCH ne ferait rien gagner, et le placer dans une feuille vue partout (règle R48) garantit l’unicité de sa valeur. Les #error rendent impossibles les combinaisons jamais testées.
Verdict
À retenir, et D1 se précise : hors PCH les réglages locaux (EngineSettings.h) ; dans config.h les commutateurs globaux, avec valeur imposée par la ligne de commande (LV3.Common.props) plutôt qu’en éditant le défaut dans le fichier.

E6pch.h — garde std::expectedÉvolution à retenir
Leçon d’origine

Dépôt actuel

Objectif de la leçon

Un header entre dans pch.h si et seulement si les deux conditions sont vraies :

Fonctionnement — ce que fait le compilateur d’un #include

Cette partie explique les mécanismes sur lesquels reposent D1, D3 et D8. Elle ne contient aucun code du moteur : seulement ce qui se passe avant que le C++ soit analysé.

1. Un #include est un copier-coller

Le préprocesseur remplace la ligne par le contenu complet du fichier, avant toute analyse du C++. Trois conséquences :

Relu à chaque foisLe texte d’un header est relu par chaque .cpp qui l’inclut. Plus il est gros, plus chaque compilation coûte : c’est ce que le PCH évite.
Les macros se propagentUne macro définie dans ce texte vaut pour tout ce qui suit dans la même unité de compilation, y compris les headers inclus après. C’est le mécanisme de min et max de windows.h (D3).
#pragma onceIl empêche seulement de coller le même fichier deux fois dans la même unité. Il ne dit rien du coût de relecture entre unités.

2. Où le compilateur cherche le fichier

Ordre documenté par Microsoft pour MSVC :

FormeOrdre de recherche
#include "x.h"1. le dossier du fichier qui contient la directive ; 2. les dossiers des fichiers qui l’ont inclus (parent, puis grand-parent…) ; 3. chaque /I, dans l’ordre ; 4. la variable INCLUDE
#include <x.h>1. chaque /I, dans l’ordre ; 2. la variable INCLUDE

La recherche s’arrête au premier fichier trouvé. Si rien n’est trouvé, l’erreur est C1083. Dans Visual Studio, « Répertoires Include supplémentaires » alimente les /I ; ceux du SDK et de la STL viennent des répertoires VC++.

3. Le header précompilé : ce que font /Yc et /Yu

pch.cppcompilé avec /Yc
LibraryV3.pchétat du compilateur après pch.h
chaque .cppcompilé avec /Yu

Avec /Yc, le compilateur analyse pch.h une fois et sauvegarde son état dans le fichier .pch. Avec /Yu, chaque autre .cpp charge cet état au lieu de relire la STL. Deux règles en découlent :

  • #include "pch.h" doit être la première ligne du .cpp : le compilateur ignore tout ce qui précède cette ligne, et l’absence de la ligne produit l’erreur C1010.
  • Si un header du PCH change, le .pch est régénéré et tous les .cpp en /Yu sont recompilés. Un header hors PCH ne recompile que ses includeurs.

SceneTypes.h — ELayerMask avec opérateurs bitmask
uint32_t = 32 couches · opérateurs obligatoires
🎯 Pourquoi : enum class bloque |, & et ~ par défaut — c’est voulu pour éviter les conversions implicites. Mais un bitmask a besoin de ces opérations. Solution : surcharge inline en dehors du namespace, sans coût runtime.
✓ Scene/SceneTypes.h (hors pch.h)
namespace LV3 {

enum class ELayerMask : uint32_t  // uint32_t = 32 couches max (comme Unity)
{
    None     = 0,
    Default  = 1 << 0,   // 0x00000001
    UI       = 1 << 1,   // 0x00000002
    Physics  = 1 << 2,   // 0x00000004
    Raycast  = 1 << 3,   // 0x00000008
    FX       = 1 << 4,   // 0x00000010
    Editor   = 1 << 5,   // 0x00000020
    All      = ~0u        // 0xFFFFFFFF
};

// Surcharges obligatoires — enum class bloque ces ops par défaut
inline ELayerMask operator|(ELayerMask a, ELayerMask b) {
    return static_cast<ELayerMask>(
        static_cast<uint32_t>(a) | static_cast<uint32_t>(b));
}
inline ELayerMask operator&(ELayerMask a, ELayerMask b) {
    return static_cast<ELayerMask>(
        static_cast<uint32_t>(a) & static_cast<uint32_t>(b));
}
inline ELayerMask operator~(ELayerMask a) {
    return static_cast<ELayerMask>(~static_cast<uint32_t>(a));
}

inline bool HasLayer(ELayerMask mask, ELayerMask layer) {
    return (mask & layer) != ELayerMask::None;
}

} // namespace LV3

0 = désactivé · define existe toujours
🎯 Pourquoi : avec #ifdef, désactiver une feature oblige à supprimer le #define — ce qui crée des références pendantes partout où le symbole était utilisé.
