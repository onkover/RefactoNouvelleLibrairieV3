Lot L02-C

Reverse-Z, pas à pas

Décision C de la Leçon 02 — la profondeur en [0,1] inversée.
Mise en œuvre : Maths/Projection.cpp (L05), Rendering/DepthBuffer.h et ClipVertex.h (L04 P2).

1. Pourquoi ce lot

Tu construis une scène : un sol, des rochers, un système solaire. Tu recules la caméra. Et au-delà d’une certaine distance, les surfaces commencent à clignoter : deux triangles qui devraient être nettement l’un derrière l’autre se disputent le même pixel, et le gagnant change d’une frame à l’autre. Les toits scintillent, le terrain fait des taches, les faces arrière traversent les faces avant.

Ce symptôme a un nom — le z-fighting — et une cause unique : le tampon de profondeur n’a plus assez de valeurs distinctes pour séparer deux surfaces proches l’une de l’autre, à cette distance-là.

Le réflexe du débutant est de rapprocher le plan far, ou d’éloigner le plan near. Ça marche, et ça coûte la scène : soit les objets lointains disparaissent, soit la caméra ne peut plus s’approcher de rien. On déplace le problème.

Ce lot résout le problème sans rien sacrifier. Pas un octet de mémoire en plus, pas un cycle CPU en plus. Juste deux coefficients écrits autrement dans la matrice de projection, et deux comparaisons retournées. Le gain va de ×8 à 1 mètre à ×8000 à 1 kilomètre.

Et comme c’est une décision qui touche la matrice de projection, le clipping, le Z-buffer et le test de profondeur en même temps, elle doit être prise une fois, au début. La changer plus tard, c’est toucher quatre fichiers et casser tous les tests de rendu d’un coup. D’où sa place en Leçon 02 et son statut de décision dictatoriale.

Deux acquis de la Leçon 02 sont des préconditions du reverse-Z, pas des détails de style :

  • float partout. On verra en §6.4 que le reverse-Z est contre-productif sur un buffer de profondeur en entier.

3. Contexte et objectif fonctionnel

Ce que la fonction doit garantir

Contrat : « pour deux surfaces distantes d’un écart réaliste (quelques millimètres sur un mur, quelques centimètres sur un terrain), le moteur doit toujours savoir laquelle est devant — à 10 cm de la caméra comme à 1 km. »

Exprimé en chiffres : l’incertitude de profondeur doit rester inférieure au millimètre sur toute la profondeur du frustum, avec near = 0,1 m et far = 1000 m.

Les trois décisions prises dans ce lot

Décision 1

NDC z ∈ [0,1]

pas [-1,1]

Décision 2

near → 1, far → 0

test GREATER

Décision 3

far infini possible

z = n / distance

Ce que ce lot ne fait pas

  • Il ne change rien à X et Y, qui restent dans [-1,+1] — le frustum est symétrique, et la précision du float est maximale au centre de l’écran, là où l’œil regarde.
  • Il ne traite pas le depth bias / polygon offset (décals, ombres). C’est un autre sujet, qui héritera simplement du signe inversé.
  • Il ne traite pas le depth prepass ni l’early-Z hiérarchique. Ce sont des optimisations ultérieures qui s’appuieront sur ce lot.

5. L’algorithme initial, et ce que ce lot y change

L’algorithme de profondeur est le même avant et après — c’est une chaîne en cinq maillons. Ce lot ne change aucun maillon : il change quatre constantes et deux signes de comparaison à l’intérieur des maillons existants.

5.1 — Construction de la matrice de projection

AVANT — OpenGL historique, NDC z ∈ [-1,+1] (le legacy LibV2)
Matrix44f m = Zeroed();
m[0][0] = (2.0f * n) / (r - l);
m[1][1] = (2.0f * n) / (t - b);
m[2][0] = (r + l) / (r - l);
m[2][1] = (t + b) / (t - b);
m[2][2] = -(f + n) / (f - n);   // near -> -1, far -> +1
m[2][3] = -1.0f;
m[3][2] = -(2.0f * f * n) / (f - n);
m[3][3] =  0.0f;
APRÈS — LV3, NDC z ∈ [0,1] reverse-Z (Maths/Projection.cpp)
Matrix44f m = Zeroed();
m[0][0] = (2.0f * n) / (r - l);
m[1][1] = (2.0f * n) / (t - b);
m[2][0] = (r + l) / (r - l);
m[2][1] = (t + b) / (t - b);
m[2][2] = n / (f - n);           // REVERSE-Z : near -> 1, far -> 0
m[2][3] = -1.0f;                 // inchangé — recopie -z dans w (main droite)
m[3][2] = (n * f) / (f - n);
m[3][3] =  0.0f;

Deux coefficients. C’est tout. m[0][0], m[1][1], m[2][0], m[2][1], m[2][3] et m[3][3] sont identiques : X et Y ne sont pas concernés, et la recopie de -z dans w est une propriété de la main droite, pas du mapping de profondeur.

5.2 — Distance au plan near, en espace de clip

AVANT — la forme canonique Direct3D standard
float NearDistance(const ClipVertex& v) noexcept
{
    return v.clip.z;        // near : z >= 0   (far : z <= w)
}
APRÈS — Rendering/ClipVertex.h
float NearDistance(const ClipVertex& v) noexcept
{
    return v.clip.w - v.clip.z;   // reverse-Z : w - z est le plan NEAR
}

Le volume de clip reste 0 ≤ z ≤ w dans les deux cas. Ce qui change, c’est lequel des deux bords est le near. En reverse-Z, z = w est le near, donc la distance signée au near est w − z.

StreamFill (stores non temporels) est un gain du chantier Clear de la phase G, indépendant du reverse-Z. Ce qui appartient à ce lot, c’est uniquement la valeur 0.0f au lieu de 1.0f, et <= au lieu de >=.

6. Comment ça marche

6.1 — Deux non-linéarités, et le choix de les faire se compenser

Non-linéarité n°1 : la projection stocke 1/z, pas z.
La matrice de projection ne range pas la distance dans le buffer : elle range son inverse, parce que la division par w intervient après. Conséquence directe : avec n = 0,1 et f = 1000, la moitié de la plage [0,1] est consommée par les 20 premiers centimètres. Tout le reste de la scène se partage l’autre moitié.

Non-linéarité n°2 : le float est un logarithme déguisé.
Un float IEEE-754 s’écrit signe × 1,mantisse × 2^exposant. Entre deux puissances de 2 consécutives, il y a toujours exactement 2²³ = 8 388 608 valeurs — que l’intervalle mesure 0,5 ou 2⁻³⁰. La densité explose donc en s’approchant de zéro.

IntervallePas du flottantValeurs distinctes
[0 ; 0,001]jusqu’à 1,4e-45≈ 1 000 000 000
[0,999 ; 1,0]5,96e-8≈ 16 800
[-1,0 ; -0,999]5,96e-8≈ 16 800

Facteur 60 000 entre les deux bouts de la plage [0,1].

Le raisonnement tient en une phrase. La projection écrase le lointain : c’est là qu’il faut le plus de valeurs disponibles. Le float a le plus de valeurs près de zéro. Donc on place le far à zéro. Les deux courbes, chacune en 1/x à sa manière, se compensent.

6.2 — Le point que tout le monde rate : la dérivée est identique

Posons d la distance à l’œil (positive), n le near, f le far.

z en fonction de ddérivée |dz/dd|
Standardz = f/(f−n) · (1 − n/d)n·f / ((f−n)·d²)
Reversez = n/(f−n) · (f/d − 1)n·f / ((f−n)·d²)

Elles sont égales. Démonstration en deux lignes : poser A = f/(f−n) et B = n/(f−n). Alors z_std = A − A·n/d, donc dz_std/dd = A·n/d² = n·f/((f−n)d²). Et z_rev = B·f/d − B, donc dz_rev/dd = −B·f/d² = −n·f/((f−n)d²). Même module.

Autrement dit : la sensibilité géométrique est rigoureusement la même. Le reverse-Z ne « redistribue » pas la profondeur. Il ne change pas d’un iota la façon dont la projection écrase le lointain.

L’incertitude en distance monde d’un pas de flottant vaut :

Δd = ulp(z) / |dz/dd|

Le dénominateur est identique dans les deux schémas. Toute la différence vient donc de ulp(z) seul — c’est-à-dire de l’endroit où la valeur atterrit dans l’espace des flottants. Le reverse-Z est une décision de placement, pas de calcul. C’est précisément pour ça qu’il est gratuit.

6.3 — Pourquoi le [0,1] est une précondition, pas une préférence

En NDC [-1,+1], les deux extrémités de la plage ont une magnitude voisine de 1. Donc ulp(-1) = ulp(+1) = 1,19e-7. Inverser le mapping échange deux emplacements de densité identique : le gain est exactement ×1.

Essaie le bouton NDC [-1,1] dans le schéma §4 : les deux rangées deviennent jumelles.

C’est la raison historique pour laquelle le reverse-Z n’existait pas sous OpenGL. OpenGL a rétropédalé en 2014 avec glClipControl(GL_LOWER_LEFT, GL_ZERO_TO_ONE) — une extension dont l’unique raison d’être est de rendre le reverse-Z possible. Vulkan, lui, ne propose même plus le [-1,1].

6.4 — Pourquoi le buffer float est l’autre précondition

Un Z-buffer en entier 24 bits (le D24 des GPU) est uniforme : le pas vaut 2⁻²⁴ partout, de 0 à 1. Aucune zone n’est plus dense qu’une autre.

Dans ce cas, le raisonnement s’effondre : il n’y a plus de non-linéarité n°2 à faire compenser. Pire, le reverse-Z devient légèrement défavorable, parce qu’on perd le seul avantage du schéma standard (la zone proche de la caméra bénéficie naturellement de la compression en 1/z).

Règle : reverse-Z et buffer flottant, ou ni l’un ni l’autre. LV3 stocke sa profondeur en std::vector<float> (DepthBuffer.h) — la condition est remplie. Essaie le bouton buffer entier 24 bits dans le schéma §4 pour voir le gain tomber à zéro.

6.5 — Le bonus : le plan far disparaît

Fais tendre f → +∞ dans les coefficients reverse-Z :

m[2][2] = n / (f - n)      ⟶  0
m[3][2] = n * f / (f - n)  ⟶  n

Les deux limites sont finies et parfaitement conditionnées. Il en résulte la formule la plus simple de tout le pipeline :

z_ndc = n / distance

Plus de plan far du tout. Plus de clipping far, plus de réglage du ratio n/f, plus d’objets lointains qui s’évanouissent quand on monte sur une colline. C’est PerspectiveInfinite() dans Projection.cpp.

En Z standard, la même limite donne m[2][2] → -1 et m[3][2] → -2n : ça compile, mais toute la scène lointaine s’agglutine sur les quelques milliers de flottants disponibles près de 1. Le far infini n’est utilisable que grâce au reverse-Z.

static_assert(sizeof(float) == sizeof(int32_t));

int32_t FloatsBetween(float a, float b) noexcept   // 0 <= a <= b
{

Étape 2Dériver les coefficients m22 et m32
Objectif : trouver les deux nombres qui envoient near → 1 et far → 0. On ne les recopie pas d’un tutoriel : on les résout, pour pouvoir les reconstruire sans Internet.

Entrée — de l’étape 1

Intervalle cible [0,1], orientation inversée.
Convention L02 : vecteur-ligne, main droite, w = −z.

Sortie

m22 = —
m32 = —

Un sommet en espace de vue a z < 0 (main droite, on regarde vers −Z). Avec le vecteur-ligne, seules deux cases entrent dans clip.z :

clip.z = z · m22 + 1 · m32
clip.w = z · m23 = -z            // m23 = -1, propriété de la main droite

z_ndc  = clip.z / clip.w = (z·m22 + m32) / (-z)

Deux contraintes, deux inconnues :

z = -n  →  z_ndc = 1   →  (-n·m22 + m32) /  n  = 1   →  m32 - n·m22 = n
z = -f  →  z_ndc = 0   →  (-f·m22 + m32) /  f  = 0   →  m32 = f·m22

Substitution : f·m22 − n·m22 = n, donc :

m22 = n / (f - n)
m32 = f · m22 = n·f / (f - n)

Vérification de signe — le piège. f > n > 0, donc m22 et m32 sont tous deux positifs. Un signe − qui traîne (par mimétisme avec la formule OpenGL, où les deux sont négatifs) retourne la profondeur : la scène s’affiche à l’envers, le plus loin devant. Écrire -n/(f-n) est l’erreur la plus fréquente de ce lot.

// Plus rapide ET plus précis que mul puis add séparés.

const __m256 vClipW = _mm256_xor_ps(vZ, kSign);

_mm256_store_ps(clipZOut + i, vClipZ);
_mm256_store_ps(clipWOut + i, vClipW);

// On veut un masque de bits, pas un if par triangle.

const __m256 d1 = _mm256_sub_ps(w1, z1);

// _CMP_LT_OQ : "< , ordonné, non signalant". Un NaN répond false partout,
// donc un triangle dégénéré n'est jamais rejeté par accident ici.
const int32_t out0 = _mm256_movemask_ps(_mm256_cmp_ps(d0, zero, _CMP_LT_OQ));
const int32_t out1 = _mm256_movemask_ps(_mm256_cmp_ps(d1, zero, _CMP_LT_OQ));
const int32_t out2 = _mm256_movemask_ps(_mm256_cmp_ps(d2, zero, _CMP_LT_OQ));

const int32_t rejectAll = out0 & out1 & out2;   // 3 sommets dehors -> rejet trivial
const int32_t acceptAll = ~(out0 | out1 | out2) & 0xFF;  // 0 dehors -> accept trivial
const int32_t needClip  = ~(rejectAll | acceptAll) & 0xFF;  // le reste : chemin lent

Le découpage lui-même (Sutherland-Hodgman) reste scalaire : il produit un nombre variable de sommets par triangle, ce que le SIMD ne sait pas faire sans compactage. On vectorise le tri, pas le découpage — et on compte sur le fait que needClip est presque toujours nul.

    ClearKernel::StreamFill(m_Data.data(), m_Data.size(), 0.0f);

Vectorisé — AVX2, 8 pixels d’une ligne

// Le Z-buffer est contigu par ligne : Row(y) donne le float* de départ,
// donc 8 pixels voisins = UN load aligné. C'est la cacheline qui commande.
const __m256 vDst = _mm256_load_ps(depthRow + x);        // profondeurs déjà écrites

// _CMP_GT_OQ : "> , ordonné". Un NaN (triangle dégénéré) échoue le test
// au lieu de corrompre le buffer. C'est voulu : jamais _CMP_GT_UQ ici.
const __m256 vPass = _mm256_cmp_ps(vZ, vDst, _CMP_GT_OQ);

// On combine avec le masque de couverture du triangle (edge functions) :
// un pixel n'écrit que s'il est DANS le triangle ET devant.
const __m256 vWrite = _mm256_and_ps(vPass, vCoverage);

// blend + store : écrit les couloirs gagnants, laisse les autres intacts.
// Préféré à maskstore, nettement plus lent sur plusieurs micro-architectures.
_mm256_store_ps(depthRow + x, _mm256_blendv_ps(vDst, vZ, vWrite));

const int32_t writeMask = _mm256_movemask_ps(vWrite);   // -> shading des 8 pixels

Sortie

Matrix44f PerspectiveInfinite(float fovYRad, float aspect, float n) noexcept
{
    const float th = std::tan(fovYRad * 0.5f);

    Matrix44f m = Zeroed();
    m[0][0] = 1.0f / (aspect * th);
    m[1][1] = 1.0f / th;
    m[2][2] = 0.0f;      // limite de n/(f-n) quand f -> +inf
    m[2][3] = -1.0f;
    m[3][2] = n;         // z_ndc = n / distance
    m[3][3] = 0.0f;
    return m;
}

Conséquence à ne pas oublier : ViewData::hasFarPlane doit valoir false pour cette lentille, et le frustum culling ne doit alors tester que 5 plans. Un sixième plan calculé depuis une matrice sans far produit des coefficients nuls et rejette tout, ou rien, selon la convention de normalisation.

8. Contre-exemples chiffrés — ce qu’il ne faut pas faire

Contre-exemple 1 — Inverser le Z en gardant le NDC [-1,+1]

« J’inverse le mapping, mais je garde l’intervalle OpenGL, ça marchera quand même. » Non : le gain est exactement ×1.

Schémaz stockéulp(z)incertitude

Les deux bords de [-1,+1] ont la même magnitude, donc le même ulp. On a payé une réécriture complète du clipping et du test de profondeur pour zéro gain. Le [0,1] n’est pas une préférence de style : c’est la condition d’existence du reverse-Z.

Contre-exemple 2 — Reverse-Z sur un buffer entier 24 bits

« Je passe mon Z-buffer en uint32 pour gagner de la bande passante, et je garde le reverse-Z. » Le reverse-Z devient inutile, et même très légèrement nuisible.

Bufferpas de quantificationincertitude stdincertitude reverse

Un entier est uniforme : il n’y a plus de non-linéarité n°2 à compenser. La règle est binaire — reverse-Z et float, ou ni l’un ni l’autre.

Contre-exemple 3 — Changer la matrice sans changer le Clear()

Le bug le plus coûteux de ce lot, parce qu’il ne ressemble pas à un bug de profondeur.

Leçon de méthode : ces quatre lignes vivent dans quatre fichiers différents (Projection.cpp, ClipVertex.h, DepthBuffer.h, RenderTypes.h). C’est précisément pour ça que le reverse-Z est une décision dictatoriale prise une fois et jamais rediscutée : il n’existe pas d’état intermédiaire fonctionnel entre les deux schémas.

9.1 — Tests hors moteur (aucun rendu, aucune fenêtre)

// Test 1 — les bornes. Si celui-ci échoue, rien d'autre ne sert à rien.
const Matrix44f P = Projection::Perspective(ToRad(60.0f), 16.0f/9.0f, 0.1f, 1000.0f);

auto NdcZ = [&](float dist) {
    const Vec4f v = MulRow(Vec4f{0,0,-dist,1}, P);
    return v.z / v.w;
};

LV3_ASSERT(ApproxEqual(NdcZ(0.1f),    1.0f, 1e-5f));   // near -> 1
LV3_ASSERT(ApproxEqual(NdcZ(1000.0f), 0.0f, 1e-5f));   // far  -> 0

// Test 2 — la MONOTONIE. Plus loin = z strictement plus petit.
// C'est le test qui attrape un signe inversé, que les bornes laissent passer
// quand on a inversé DEUX fois par erreur.
float prev = NdcZ(0.1f);
for (float d = 0.2f; d < 1000.0f; d *= 1.2f) {
    const float z = NdcZ(d);
    LV3_ASSERT(z < prev && "reverse-Z : z doit DÉCROÎTRE avec la distance");
    prev = z;
}

// Test 3 — le gain de précision, mesuré et pas supposé.
// Deux surfaces à 1 mm l'une de l'autre, à 100 m : elles DOIVENT
// produire deux flottants distincts.
LV3_ASSERT(NdcZ(100.0f) != NdcZ(100.001f));

// Test 4 — le far infini reste cohérent.
const Matrix44f Pi = Projection::PerspectiveInfinite(ToRad(60.0f), 16.0f/9.0f, 0.1f);
auto NdcZi = [&](float d) { const Vec4f v = MulRow(Vec4f{0,0,-d,1}, Pi); return v.z/v.w; };
LV3_ASSERT(ApproxEqual(NdcZi(0.1f), 1.0f, 1e-5f));
LV3_ASSERT(NdcZi(1e6f) > 0.0f && NdcZi(1e6f) < 1e-6f);   // tend vers 0, jamais négatif

// Test 5 — le clipping near, forme canonique.
LV3_ASSERT(NearDistance(ClipVertex{MulRow(Vec4f{0,0,-0.05f,1}, P)}) < 0.0f);  // devant le near -> rejeté
LV3_ASSERT(NearDistance(ClipVertex{MulRow(Vec4f{0,0,-500.f,1}, P)}) > 0.0f);  // dans le frustum -> gardé

9.3 — Vérification visuelle

  • ERenderMode::Depth — en reverse-Z, le proche est clair et le lointain sombre. Si c’est l’inverse, un signe a sauté. (En Z standard c’était le contraire : voilà pourquoi ce mode de debug doit être relu après ce lot.)
  • ERenderMode::LinearDepth — reconstruit la distance réelle depuis z_ndc : d = n·f / (z·(f−n) + ... ). Il doit donner un dégradé visuellement linéaire entre near et far. Un dégradé qui s’écrase près de la caméra signale que la formule de reconstruction est restée celle du Z standard.
  • Deux quads coplanaires séparés de 1 mm, placés à 500 m : en Z standard ils clignotent, en reverse-Z ils sont nets et stables. C’est le test de non-régression le plus parlant à garder dans la scène de debug.
