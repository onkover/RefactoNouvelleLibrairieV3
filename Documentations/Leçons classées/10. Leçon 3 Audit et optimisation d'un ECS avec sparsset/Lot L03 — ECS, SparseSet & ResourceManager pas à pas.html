1 · Pourquoi ce lot existe

Ce qui a déjà été fait

L01 a posé le socle du projet (en-tête précompilé, configuration Visual Studio, énumérations). L02 a posé les mathématiques (Vec3f, Matrix44f, Quatf). L’ordre des leçons a ensuite changé : avant de calculer des matrices de caméra et de dessiner des triangles, il faut savoir où vivent les objets de la scène et comment on les parcourt. D’où ce lot, placé avant caméra/frustum et rasterizer.

Le contexte

Le moteur est 100 % CPU : chaque cycle perdu à attendre la mémoire est un cycle de moins pour le rasterizer. Une scène contient des centaines ou milliers d’objets (planètes, caméra, lumières, déclencheurs). À chaque image, des systèmes doivent les animer, composer leurs matrices, tester leurs collisions, puis les dessiner. L’ancien moteur utilisait un graphe de nœuds (objets alloués un par un, hiérarchie d’héritage). Le dépôt contenait déjà un ECS à sparse set, un Registry et un ResourceManager à handles typés : ce lot les a audités, corrigés et prouvés.

L’objectif fonctionnel

  • Stocker et retrouver les données d’un objet en temps constant, sans cache miss inutile.
  • Parcourir « tous les objets qui ont un Transform et un Mesh » à vitesse maximale, y compris quand la scène change.
  • Supprimer un objet sans corrompre la scène : un objet détruit ne doit jamais être confondu avec celui qui prend sa place.
  • Charger une ressource une seule fois (mesh, matériau, texture) et la référencer depuis les composants sans jamais la posséder.

Pourquoi c’est important pour la suite

Tous les lots suivants (matrices caméra, frustum, culling, rasterizer) lisent ces structures. Une erreur ici ne plante pas : elle produit des résultats presque justes (mauvais composant lu, mesh perdu, scène qui dérive). Corriger plus tard coûterait dix fois plus.

Cet artefact reste lisible un an plus tard : il pose d’abord le contexte et les décisions, puis la méthode, puis un laboratoire à manipuler, puis le détail technique étape par étape. Tout le lot reste dans le sujet de L03 ; quand une notion de lot supérieur remet une décision en cause, elle est notée dans la section 8 (roadmap) sans être traitée ici.

2 · La méthode : un ECS à sparse set

Ce que c’est, vulgarisé

Imagine un entrepôt avec un rayon par type de pièce (un rayon « Transform », un rayon « Mesh »…). Dans chaque rayon, les pièces sont rangées sans aucun trou, côte à côte. Un registre d’accueil (le « sparse ») dit, pour chaque objet de la scène, à quelle place se trouve sa pièce dans chaque rayon, ou « rien ». Un second carnet (le « miroir ») dit, pour chaque place du rayon, à quel objet elle appartient. Un objet n’est qu’un numéro de ticket ; ce qu’il « est » dépend uniquement des rayons où il possède une pièce.

Sources et usage

  • Structure de données : sparse set, décrite par Preston Briggs et Linda Torczon, « An Efficient Representation for Sparse Sets », ACM Letters on Programming Languages and Systems, 1993.
  • Application à l’ECS : bibliothèque EnTT de Michele Caini (« skypjack »), github.com/skypjack/entt, et sa série d’articles « ECS back and forth » (skypjack.github.io). Le README d’EnTT cite notamment Minecraft parmi ses utilisateurs.
  • Variante concurrente : les archetypes (Unity DOTS, Flecs, Unreal Mass), où les entités de même « signature » de composants vivent ensemble.

Il n’y a pas de gagnant absolu : le sparse set est le meilleur compromis simplicité / ajout-suppression rapides ; les archetypes gagnent en itération pure mais coûtent cher à chaque changement de composition. Pour un moteur pédagogique où la composition d’une entité change peu, le sparse set est le bon choix — et on pourra passer aux groupes plus tard sans changer l’API.
