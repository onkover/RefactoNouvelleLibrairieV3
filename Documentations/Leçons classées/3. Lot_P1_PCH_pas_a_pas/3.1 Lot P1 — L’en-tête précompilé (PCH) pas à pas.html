Lot P1 — L’en-tête précompilé (PCH), pas à pas

Objectif. Comprendre ce que fait réellement Visual Studio avec pch.h, pch.cpp et LibraryV3.pch, pour ne plus jamais subir l’erreur C1083 et savoir quoi mettre (ou ne pas mettre) dans le PCH.

Introduction. Sans PCH, chaque .cpp relit et ré-analyse toute la STL. Avec PCH, un seul fichier (pch.cpp) fait ce travail et fige l’état du compilateur dans LibraryV3.pch. Tous les autres le rechargent. La mécanique est simple, mais elle repose sur un ordre strict : quelqu’un doit écrire le .pch avant que les autres le lisent.

3. Contre-exemples chiffrés


Contre-exemple 1 : pch.cpp en /Yu (ton erreur)

  
pch.cpp : Use   →  cl /Yu"pch.h" … pch.cpp   →  C1083

  
Les  fichiers sont en Use, aucun n’écrit le .pch. Résultat chiffré, quel que soit le nombre de cœurs :  erreurs C1083 (identiques), 0 .obj, 0 .lib. Tu as vu la première ; la liste complète en contient autant que de fichiers. Corriger un seul fichier (pch.cpp) les supprime toutes : une seule cause.

6. Questions de fond



  
Pourquoi « No such file or directory » et pas une erreur de réglage ?

  
Le compilateur ne connaît pas ton intention. Il lit la ligne de commande /Yu"pch.h" /Fp"x64\Debug\LibraryV3.pch", va chercher ce fichier, ne le trouve pas, et s’arrête. Il n’a aucun moyen de savoir qu’un autre fichier aurait dû le produire. Le message décrit le symptôme (fichier absent), jamais la cause (personne ne l’a écrit).

  
Pourquoi un seul créateur ?

  
Le .pch est un instantané binaire de l’état interne du compilateur après l’analyse de pch.h. Il y a un fichier de sortie par configuration : deux sources qui l’écriraient ne donneraient aucune garantie sur celui qui reste, surtout avec /MP. Règle : un /Yc par configuration, rien d’autre.

  
Pourquoi Debug et Release séparément ?

  
Les propriétés Visual Studio sont stockées par couple configuration|plateforme. Corriger Debug|x64 ne touche pas Release|x64. Dans la boîte de propriétés, choisis « Toutes les configurations » ou corrige les deux.

  
Correction d’une affirmation de mon message précédent

  
Je t’ai dit que tout ce qui précède #include "pch.h" (commentaire, #pragma once…) pouvait faire échouer la compilation. C’était imprécis. Les commentaires sont sans effet. Pour un fichier en /Yu, le compilateur ignore silencieusement toutes les directives du préprocesseur placées avant l’include (#define, #pragma…). Pas d’erreur : le code compile, mais sans ton #define. C’est plus dangereux qu’une erreur : voir le contre-exemple 3.

  
Un commutateur passé par /D recompile-t-il tout, où qu’il soit lu ? (ajout du lot L01, partie B)

  
Oui. LV3.Common.props qui pose /DLV3_PROFILE=1 change la ligne de commande de chaque .cpp de la LIB et de l’EXE. MSBuild mémorise la ligne de commande de chaque fichier (fichiers .tlog) : si elle diffère, il recompile, pch.cpp compris, que le symbole soit lu dans config.h (dans le PCH) ou dans un seul .cpp. Le placement du #define ne change donc rien au coût d’un commutateur de build ; il change la garantie d’unicité de sa valeur (écart E4 du lot L01, bug 0.3). Le PCH ne fait payer « trop » que pour une valeur éditée dans un header du PCH et lue par peu de fichiers : c’est elle qui doit sortir du PCH (EngineSettings.h).

  
Troisième cas, le moins cher : une valeur lue dans engine.json ne passe par aucun compilateur. La modifier ne recompile rien ; il suffit de relancer (lot L01, partie B, DB1).

  
Piège à anticiper pour tes kernels AVX2 / AVX-512

  
Le .pch fige l’état du compilateur avec ses options. Si tu compiles un fichier avec des options différentes des autres (par exemple /arch:AVX512 uniquement sur un fichier de kernels), le compilateur peut refuser de réutiliser le .pch (erreur du type « option incohérente avec l’en-tête précompilé », C2855 typiquement). Le comportement exact dépend de l’option : à tester par un build quand tu arriveras à ces fichiers. Solution usuelle : NotUsing pour ce seul fichier, ou ses propres options regroupées sur un petit nombre de fichiers.
