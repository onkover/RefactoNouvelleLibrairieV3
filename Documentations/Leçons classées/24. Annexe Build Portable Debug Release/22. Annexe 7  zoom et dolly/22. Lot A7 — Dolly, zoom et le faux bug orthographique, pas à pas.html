Lot A7 — Dolly, zoom et le faux bug orthographique, pas à pas

Une caméra orthographique « refuse » d’avancer. Elle avance pourtant. Comprendre pourquoi l’écran ne peut pas le montrer, puis donner à la molette le geste qui manquait : le zoom.

0 · Pourquoi ce lot

Le constat de départ est simple et paraît accablant : avec une caméra perspective, les flèches avant/arrière font avancer et reculer la vue. Avec une caméra orthographique, droite/gauche fonctionne, mais avant/arrière ne produit rien à l’écran. Tout pousse à conclure à un bug du contrôleur clavier.

Ce lot existe pour deux raisons, de natures très différentes :

  1. Une leçon de diagnostic. Le contrôleur n’est pas fautif, la matrice non plus. L’orthographique est mathématiquement incapable de montrer un déplacement le long de son axe de visée. Ce n’est pas un défaut, c’est sa définition. Corriger le contrôleur ou la matrice aurait détruit une propriété dont le reste du moteur dépend (les gizmos de l’A5, la section constante).
  2. Une commande qui manquait. Puisque « avancer » ne peut rien montrer en orthographique, il faut un autre geste pour cadrer plus serré ou plus large : le zoom. Il était même prévu — InputState::wheelDelta portait le commentaire « molette : zoom / vitesse » — mais aucun système ne le lisait.
Ce que livre le lot. Aucune ligne modifiée dans le contrôleur ni dans les matrices de projection. Un nouveau système, CameraZoomSystem (Scene/System.cpp) ; un commentaire d’en-tête rectifié dans CameraComponent ; une TNR de huit sections, TestCameraZoom (EXE). Et, pendant le même échange, deux incidents qui n’avaient rien à voir avec le zoom mais qui ont été pris pour lui (§9).
À relire dans un an. Si un déplacement clavier « ne fait rien », la première question n’est pas « que fait le contrôleur ? » mais « qu’est-ce que la projection est capable de montrer ? ». Ce lot est la démonstration complète de cette question.

5 · La technique

5.1 La preuve est dans la matrice

Les deux fabriques de Maths/Projection.cpp, réduites à ce qui produit la coordonnée verticale (même raisonnement pour x, avec l’aspect en plus) :

// Perspective (vecteur-ligne)
m[1][1] = 1 / tan(fovY / 2);
m[2][3] = -1;          // recopie -z_vue dans w
// clip.y = y_vue · m11
// clip.w = -z_vue
// ndc.y  = y_vue · m11 / (-z_vue)
// Orthographique (OrthographicCentered)
m[1][1] = 2 / orthoHeight;
// m[2][3] = 0 : w reste à 1
// clip.y = y_vue · m11
// clip.w = 1
// ndc.y  = y_vue · m11       ← aucun z

En perspective, z_vue divise : approcher la caméra réduit -z_vue, l’objet grossit et s’écarte du centre. En orthographique, w = 1 pour tous les sommets ; z_vue n’entre que dans ndc.z (la profondeur). Translater la caméra le long de son axe change z_vue de tous les sommets… et ne change ndc.x ni ndc.y d’aucun. La caméra bouge ; l’écran ne peut pas le dire, sauf quand un objet franchit le near ou le far, ou quand deux objets échangent leur ordre de profondeur.

Même cause, deux symptômes. C’est la section constante de l’A5 §2.4 : le gizmo ortho est une boîte (section indépendante de la distance), le gizmo perspective une pyramide. Ici, le symptôme est un dolly invisible. Corriger l’un sans l’autre est impossible : c’est la même propriété.

Laboratoire — vue de côté, calculs en float32

Deux objets : A (hauteur 2, à z = 0) et B (hauteur 6, à z = −40), demi-taille 1. La caméra regarde vers −z. Déplacez-la (dolly), changez la lentille (zoom), comparez.

5.2 Dolly et zoom : parallaxe contre homothétie

Le laboratoire montre la différence qui justifie deux commandes séparées :

  • Le zoom multiplie m11 : tous les ndc sont multipliés par le même facteur. C’est une homothétie de l’image, centrée sur l’axe de visée. Les rapports de taille entre A et B ne changent pas.
  • Le dolly (en perspective) change -z_vue d’une même quantité pour tous les sommets, mais la division fait varier chaque objet différemment selon sa distance : A, proche, grossit beaucoup ; B, lointain, à peine. C’est la parallaxe.
  • L’effet Vertigo (Hitchcock, 1958) combine les deux : la caméra recule pendant que la lentille resserre, de sorte que A garde exactement sa taille. Seul B change : la profondeur « s’écrase ». C’est la preuve visuelle que dolly et zoom ne sont pas interchangeables.

5.3 Pourquoi un pas multiplicatif

Les trois grandeurs n’ont pas la même échelle : orthoHeight ≈ 120 (ou 1200 sur la scène système solaire), fovYDeg ≈ 45, focalLengthMm ≈ 35. Un pas additif fixe est imperceptible sur une grande valeur et violent (voire négatif) sur une petite. Un pas multiplicatif change la valeur du même pourcentage quelle qu’elle soit — ce que l’œil perçoit, c’est un rapport de grossissement, pas une différence.

5.4 Trois sources de vérité, et le piège de la focale

CameraFovY(cam) (L05) est l’unique fonction qui dit le fov vertical réel :

if (cam.m_lensModel == ELensModel::Filmback)
    return 2 · atan( m_filmHeightMm / (2 · m_focalLengthMm) );   // focale + pellicule
return m_fovYDeg · TO_RADIAN;                                       // angle direct

Donc, pour une lentille Filmback, m_fovYDeg n’est pas lu. Un zoom qui l’écrirait n’aurait aucun effet (CE3). Et la focale varie à l’inverse de l’angle : une focale plus longue donne un angle plus étroit, donc un zoom avant. D’où l’unique inversion du système : focal ÷ s au lieu de × s.

5.5 Pourquoi le zoom n’a pas besoin de m_dirty

Le dolly écrit m_local.position : il doit lever m_dirty, sinon LocalTransformSystem ne recuit pas m_localMatrix (contrat R11bis). Le zoom écrit dans CameraComponent, qui n’a aucune forme cuite : BuildViewData relit la lentille brute et reconstruit la projection à chaque frame. Aucun cache, donc aucun drapeau d’invalidation. Ajouter un tr.m_dirty = true dans CameraZoomSystem serait inutile — et mentirait sur ce qui a changé.

Règle. Un drapeau dirty n’a de sens que là où existe une forme cuite (un cache). Pas de cache, pas de drapeau. Le lever « par précaution » coûte une recomposition et brouille le contrat.

5.6 Portée : la caméra pilotée, pas la caméra vue

Le moteur distingue deux notions orthogonales (règle d’architecture) : active/priority (politique de rendu : qui est affichée) et enabled (contrôleur : qui reçoit les commandes). Le déplacement clavier suit FPSControllerComponent::m_isEnabled. Le zoom suit le même filtre : sinon la molette zoomerait une caméra que le clavier ne déplace pas, et réciproquement. Conséquence assumée : une caméra sans contrôleur (Overview_Camera, Top_View…) ne zoome pas. C’est la demande « pouvoir cadrer la vue de droite », notée pour plus tard (A7-5).

6 · Les étapes

Le système, déroulé ligne par ligne sur un cas que vous choisissez. Tous les calculs sont faits en float32 (Math.fround), comme le CPU. Chaque étape affiche ce qu’elle reçoit de la précédente et ce qu’elle produit.

E1 Sortie immédiate si la molette n’a pas bougé

Pourquoi : 99 % des frames n’ont aucun cran de molette. Le système ne doit rien coûter dans ce cas — pas même construire la vue ViewGroup.

Reçoit
Produit
if (in.wheelDelta == 0) return;
const float wheel = static_cast<float>(in.wheelDelta);

Pendant vectoriel : aucun, et aucun à chercher — c’est un test de branche unique par frame.

E2 Portée : seulement les caméras pilotées

Pourquoi : on zoome ce qu’on pilote. Le même filtre que le déplacement clavier (§5.6), sinon clavier et molette agiraient sur deux caméras différentes.

Reçoit
Produit
for (auto&& [entity, cam, ctrl] :
     registry.ViewGroup<CameraComponent, FPSControllerComponent>())
{
    if (!ctrl.m_isEnabled) continue;

Pendant vectoriel : aucun. ViewGroup itère le plus petit des deux pools (L03) : ici une poignée de caméras. Un parcours SoA n’a de sens qu’à partir de dizaines d’éléments homogènes ; ce sont 1 à 5 entités par frame.

E3 Crans effectifs : le sprint multiplie l’exposant

Pourquoi : Shift accélère déjà le déplacement. Le zoom doit suivre la même règle, sans constante propre : on réutilise m_sprintMultiplier du contrôleur.

Reçoit
Produit
const float effectiveWheel = wheel * (in.sprint ? ctrl.m_sprintMultiplier : 1.0f);

Pendant vectoriel : aucun (un produit scalaire par caméra).

E4 Le facteur unique : s = 0,9^e

Pourquoi : une seule constante (10 % par cran) pour trois lentilles. s < 1 en zoom avant, s > 1 en zoom arrière, s(−e) = 1/s(e) : dézoomer est l’inverse exact de zoomer (au float près, CE7).

Reçoit
Produit
constexpr float zoomRatioPerNotch = 0.90f;            // 10 % par cran
const float shrink = std::pow(zoomRatioPerNotch, effectiveWheel);

Pendant vectoriel : aucun dans le moteur. _mm256_pow_ps n’existe qu’en SVML (bibliothèque Intel) ; pour 1 à 5 valeurs par frame, l’appel scalaire powf coûte quelques dizaines de nanosecondes — moins que le chargement des registres.

E5 Aiguillage vers la source de vérité

Pourquoi : écrire dans le champ que BuildViewData lira réellement. m_projection d’abord, m_lensModel ensuite — en ortho, la lentille n’a pas de sens.

Reçoit
Produit
switch (cam.m_projection) {
case EProjectionType::Orthographic: /* m_orthoHeight */
case EProjectionType::Perspective:
    if (cam.m_lensModel == ELensModel::FieldOfView) /* m_fovYDeg */
    else                                             /* m_focalLengthMm */
}

Pendant vectoriel : aucun. En SIMD, trois branches deviennent trois calculs complets masqués par _mm256_blendv_ps : on paierait les trois pour en garder un.

E6 Application du facteur (avec l’inversion de la focale)

Pourquoi : orthoHeight et fovYDeg rétrécissent quand on zoome (×s) ; la focale allonge (÷s). L’inversion est portée par la formule, jamais par une seconde constante.

Reçoit
Produit
cam.m_orthoHeight   * shrink    // ortho
cam.m_fovYDeg       * shrink    // FOV
cam.m_focalLengthMm / shrink    // Filmback : inversé

Pendant vectoriel : aucun (un produit ou un quotient).

E7 Bornes : le clamp

Pourquoi : orthoHeight → 0 rend 2/orthoHeight infini ; fov → 180° rend tan(fov/2) infini ; fov → 0 ou focale → 0 rendent la projection dégénérée. Les bornes gardent la matrice finie quoi que fasse la molette.

Reçoit
Produit
cam.m_orthoHeight   = std::clamp(h * s, 0.5f, 5000.0f);
cam.m_fovYDeg       = std::clamp(f * s, 1.0f,  170.0f);
cam.m_focalLengthMm = std::clamp(F / s, 1.0f, 2000.0f);

Pendant vectoriel : _mm256_min_ps(_mm256_max_ps(v, lo), hi) existerait, mais pour une valeur : std::clamp compile déjà en minss/maxss.

E8 Effet en aval : la projection, et ce que voit l’étage sommets

Pourquoi : vérifier que le champ écrit est bien celui qui change l’image. On suit la valeur jusqu’au coefficient m11 de la projection, puis dans les huit couloirs de l’étage sommets.

Reçoit
Produit
// BuildViewData (System.cpp), étape 2 — scalaire, une fois par vue
const float fovY = CameraFovY(cam);
if (cam.m_projection == EProjectionType::Orthographic)
    v.projectionMatrix = Projection::OrthographicCentered(cam.m_orthoHeight, aspect, n, f);
else ...  Projection::PerspectiveInfinite(fovY, aspect, n);

Pendant vectoriel (il existe, c’est l’étage sommets) : huit sommets en SoA, une projection, une division par w couloir par couloir. Ci-dessous, huit sommets à y_vue = 1 et à des profondeurs différentes, avant et après le zoom, puis avant et après un dolly de 5 unités.

// Même principe que l'étage sommets du chantier B3 (SoA, AVX2)
__m256 vy  = _mm256_loadu_ps(yVue);          // couloirs 0..7 : y en espace vue
__m256 vz  = _mm256_loadu_ps(zVue);          // couloirs 0..7 : z en espace vue (< 0 devant)
__m256 m11 = _mm256_set1_ps(P[1][1]);        // le coefficient que le zoom vient de changer
__m256 cy  = _mm256_mul_ps(vy, m11);         // clip.y = y · m11
__m256 cw  = ortho ? _mm256_set1_ps(1.0f)    // ortho : w = 1 dans TOUS les couloirs
                   : _mm256_sub_ps(_mm256_setzero_ps(), vz);   // persp : w = -z
__m256 ny  = _mm256_div_ps(cy, cw);          // ndc.y, couloir par couloir

7 · Vérifier

7.1 Tests hors moteur — TestCameraZoom rejouée ici

Les huit sections de la TNR (EXE, Test/TestCameraZoom.cpp), recalculées en float32 avec les mêmes valeurs (orthoHeight 120, fov 45°, focale 35 mm, sprint ×3, ε = 1e-4). Chaque section construit son propre Registry : aucune ne peut faire réussir la suivante.

Faiblesse relevée (A7-7). La section §8 vérifie seulement que les valeurs restent finies et positives après ±200 crans. Elle ne vérifie pas qu’elles valent exactement la borne attendue (0,5 / 5000, 1 / 170, 1 / 2000). Une borne mal orientée (par exemple maxFov = 1) passerait. Renfort proposé, non appliqué : LV3_ASSERT(result.m_orthoHeight == 0.5f) pour « ortho zoom max », etc.

7.2 Filets Debug déjà en place

  • BuildViewData : LV3_ASSERT(std::isfinite(aspect) && aspect > 0), LV3_ASSERT(cam.m_infiniteFar || std::isfinite(v.farPlane)), LV3_ASSERT(!(ortho && infiniteFar)). Le zoom ne peut pas les déclencher : les clamps gardent m11 fini.
  • CheckControllerExclusivity (chaque frame) : un seul contrôleur actif par caméra. Le zoom ne crée pas de conflit — il n’écrit pas le Transform.
  • Test_GizmoMatchesFrustum (A5/A9) : vérifie que le gizmo suit la lentille après un zoom (en perspective : échelle 1 ; en ortho : rapport s = L/(orthoHeight/2)).

7.3 Prédictions chiffrées

Ce que vous devez lire à l’écran ou au débogueur, calculé ici en float32. Si une valeur diffère, la cause est dans la formule, pas dans l’arrondi (l’écart serait d’ordre 1, pas 1e-6).

7.4 Vérification à l’œil (validée par Onky)

  • Molette avant : le champ se resserre, dans les trois lentilles — y compris la focale, malgré la formule inversée.
  • Shift + molette : accélération nette, sans saut brutal à la butée.
  • Butées : poussées volontairement, aucun artefact, aucune division par zéro.
  • Gizmo : suit le zoom en perspective ; en ortho, ne le suit plus depuis l’A9 (normal, §9).

9 · Les incidents de l’échange, et ce que les annexes suivantes ont corrigé

Après la clôture du zoom, deux symptômes sont apparus. Ils ont d’abord été soupçonnés d’être des effets du zoom. Aucun ne l’était. Ils sont gardés ici parce qu’ils remettent en question des affirmations faites pendant cet échange.

9.1 « Je ne vois plus les objets à droite » — le drapeau dirty volé (A8)

Contexte. Seul le gizmo restait visible dans le viewport de droite. wheelDelta était à 0 et les caméras de droite n’avaient pas de contrôleur : CameraZoomSystem était matériellement hors de cause.

Cause. DebugDisplaySystemRecursive, une fonction d’affichage, baissait transform.m_dirty. Elle consommait le signal destiné à LocalTransformSystem : la matrice locale des caméras sans contrôleur restait à l’identité pour toujours. La caméra FPS survivait parce que son contrôleur relève le drapeau à chaque frame. Preuve : dans deux relevés successifs, Overview_Camera restait à (0, 0, 0) au chiffre près.

Avant
Vec3f localPosition = ...;
transform.m_dirty = false; // Reset dirty flag after displaying
std::cout << ...
Après
Vec3f localPosition = ...;
// une fonction d'affichage ne mute rien
std::cout << ...

Le bug a récidivé une fois après un retour arrière git (ligne restaurée), puis a été recorrigé. Il a donné la règle R11bis (§10). Le dépôt actuel ne contient plus la ligne.

9.2 « Le gizmo de la FPS devient démesuré » — un faux diagnostic (A9)

Cet échange s’est terminé sur une note de reprise affirmant que le gizmo de FPS_Camera grossissait en présence d’une caméra ortho à orthoHeight: 1200, sans cause trouvée. L’annexe A9 a démontré que ce titre était faux.

10 · Les règles dégagées

Dolly ≠ zoom. Le clavier écrit la position (Transform), la molette écrit la lentille (CameraComponent). Jamais l’un pour l’autre.
Écrire dans la source de vérité. Une lentille a un seul champ lu à la fois ; écrire l’autre est une écriture morte (CE3).
Grandeurs d’échelles différentes → pas multiplicatif. Même règle reprise plus tard pour le temps (S10 : l’échelle de temps est multiplicative, comme le zoom).
Une inversion vit dans la formule, pas dans une constante dupliquée. ÷ s pour la focale, un seul s.
R11bis. Seul l’écrivain de m_local lève m_dirty ; seul LocalTransformSystem, après recomposition, le baisse. Jamais un système d’affichage.
Pas de cache, pas de drapeau. Le zoom n’a pas de dirty parce que la lentille n’a pas de forme cuite (§5.5).
Principe n°13 (A9). Avant de chercher pourquoi un objet se comporte mal, vérifier quel objet. Une identification visuelle n’est pas une mesure.
Un déplacement sans effet visible n’est pas forcément un bug de déplacement. Vérifier d’abord ce que la projection peut montrer.

12 · Synthèse

Le « bug » de la caméra ortho décrivait un comportement exact : la position change, la projection n’a aucun terme qui puisse le montrer. Le vrai manque était une commande — le zoom — déjà prévue par le code mais jamais câblée. Elle tient en un système de quarante lignes qui écrit la seule source de vérité de chaque lentille, avec une seule constante et une seule inversion, verrouillées par une TNR. Le reste de l’échange a rappelé deux disciplines : une fonction d’affichage n’écrit rien, et avant de chercher la cause d’un comportement, on nomme l’objet qui le produit.
