0.1 · Pourquoi ce lot

La leçon 06 devait se clore par une mesure : combien coûtent WorldTransformSystem, la rasterisation et TriggerSystem sur trois scènes du système solaire. Cette mesure n’a jamais eu lieu, et la raison n’avait rien à voir avec le moteur.

La configuration Release|x64 n’avait jamais été construite. Pas une fois depuis la création du projet. Ce n’était pas un oubli anodin : cinq défauts indépendants l’en empêchaient, chacun suffisant à lui seul. Tant qu’ils tenaient, la seule configuration disponible était Debug — et mesurer en Debug ne mesure rien d’utile.

Le contre-exemple de départ, celui qu’il faut écarter avant tout le reste.
« On profilera en Debug, les proportions restent les mêmes. » Faux. En Debug, /Od supprime l’inlining ; ComponentView, EdgeFunction et les opérateurs de Vec3f n’existent que par l’inlining ; les itérateurs de la STL paient leurs contrôles de validité. On ne mesurerait pas le coût de WorldTransformSystem : on mesurerait le coût de ne pas inliner, dans des rapports qui ne se transposent pas. La configuration Release n’est pas une variante de Debug — c’est un programme différent.

Ce lot ne produit donc aucune fonctionnalité visible à l’écran. C’est un lot d’infrastructure, et c’est précisément ce qui le rend facile à repousser indéfiniment. Il a pourtant un rendement immédiat et mesurable : en le faisant, le compilateur a dénoncé cinq bugs réels du moteur que six mois de développement en Debug n’avaient pas révélés.

0.3 · Contexte et objectif fonctionnel

Trois propriétés manquaient au projet, et aucune n’est un détail d’outillage.

1. Le moteur doit se compiler de deux façons

Debug pour comprendre, Release pour mesurer. Deux configurations qui divergent sur dix réglages ne sont pas deux façons de compiler le même programme : ce sont deux programmes. L’objectif n’est pas « que Release compile » — c’est que Debug et Release ne diffèrent que par ce qui doit légitimement les différencier : optimisation, bibliothèque d’exécution, contrôles d’exécution. Tout le reste doit être commun par construction, pas par vigilance.

2. Le projet doit s’installer n’importe où

Onky travaille sur deux machines. Jusqu’ici, ça fonctionnait parce que les deux chemins étaient écrits dans le fichier de projet versionné, et que l’un des deux était ignoré. Ça marche à deux. Ça casse à trois, et ça casse au premier renommage de dossier — avec un message incompréhensible.

L’objectif fonctionnel, formulé comme un test : copier le dossier x64\Release\ sur une clé USB, le lancer par double-clic sur une machine qui n’a jamais vu le code source, et que la scène s’affiche.

3. Les filets doivent être pilotables indépendamment

Un seul #ifdef _DEBUG gouvernait quatre choses sans rapport : les assertions, le code d’outillage, les journaux de diagnostic et les journaux verbeux. Conséquence pratique : impossible d’activer les invariants sans réactiver le rendu console. Donc on ne les active jamais, et on mesure sans filet.

Règle R45. Tests et invariants ne se gouvernent pas par le même commutateur. Un test vérifie un comportement à la demande, hors production ; un invariant garde une propriété pendant l’exécution, y compris là où ça compte. Les lier à _DEBUG revient à décider que le code optimisé ne mérite pas de filet — c’est-à-dire à retirer le filet exactement là où on tombe.

Ce que ce lot ne traite pas

Pas de SIMD, pas de mathématiques, pas de rendu. Ce lot est entièrement dans la chaîne de construction et le démarrage. Il n’a donc ni pendant scalaire ni pendant vectorisé : il n’y a pas de boucle de calcul à dérouler. La seule décision qui touche au SIMD est le retrait du /arch: global — et elle a été renversée plus tard par le chantier B1, ce que le §Amendements documente en avant/après.

1 · La méthode : comment MSBuild construit la ligne de commande

Tout ce lot repose sur un mécanisme qu’il faut comprendre avant de toucher quoi que ce soit, parce qu’il est silencieux quand on s’y prend mal. Deux tentatives ont échoué ici avant que le montage fonctionne, et dans les deux cas trois réglages sur quatre passaient — ce qui est la pire situation possible : ça a l’air de marcher.

Le modèle

MSBuild lit un .vcxproj de haut en bas, une seule fois. À chaque <Import>, il déroule le fichier importé sur place, comme un #include. Les valeurs s’empilent et la dernière écrase la précédente.

Deux familles de valeurs, qui n’obéissent pas aux mêmes règles :

  • Les propriétés — <PropertyGroup>, exemple $(LV3BuildDir). Écrasement pur.
  • Les métadonnées d’item — <ItemDefinitionGroup><ClCompile>, exemple AdditionalOptions. Écrasement sauf si l’on écrit explicitement %(AdditionalOptions) dans la nouvelle valeur, auquel cas l’ancienne est réinjectée à cet endroit.
Règle R40. Toute métadonnée d’item définie dans un .vcxproj doit se terminer par %(NomDeLaMétadonnée). Sans lui, elle ne complète pas l’héritage : elle l’efface. C’est le même mécanisme que l’oubli de $(IncludePath) à la fin d’un IncludePath, et il est silencieux dans les deux cas.

Schéma dynamique — la chaîne d’imports

Joue avec les trois réglages ci-dessous. Chacun reproduit une situation réellement rencontrée pendant ce lot. Observe la colonne de droite : ce qui survit n’est pas ce qu’on croit.

Le fichier Microsoft.Cpp.x64.user.props est la feuille utilisateur globale de Visual Studio, dans %LOCALAPPDATA%\Microsoft\MSBuild\v4.0\. Sur cette machine, elle contenait un AdditionalOptions sans %(…) — écrit par l’IDE, qui ne l’ajoute jamais spontanément. C’est elle qui effaçait nos dix options, et elle seule, puisqu’elle ne définit ni LanguageStandard, ni WarningLevel, ni ConformanceMode.

Méthode de diagnostic. Le Gestionnaire de propriétés (Affichage → Autres fenêtres) n’affiche que les feuilles importées dans un <ImportGroup Label="PropertySheets"> : un <Import> nu est appliqué mais invisible. Le seul juge est le champ gris de Propriétés → C/C++ → Ligne de commande, qui montre la commande réellement passée à cl.exe.

Et le point de méthode à retenir : ce n’est pas le raisonnement qui a trouvé la cause. Deux hypothèses plausibles et fausses ont précédé un grep sur les fichiers de build. Ne crois pas la documentation, lis la source — la règle vaut pour le moteur comme pour l’outillage.

2 · Les étapes

Étape 1 Diagnostiquer : pourquoi Release ne construit pas
Objectif
Ne pas réparer au jugé. Lister les causes indépendantes, pour savoir combien d’obstacles séparent le projet d’une mesure — et ne pas croire que la première réparation suffira.
Entrée
Les deux .vcxproj du dépôt, lus ligne à ligne. Aucune supposition : les tables ci-dessous viennent du fichier.
#CauseErreur produite

3Includes, dossiers de bibliothèques et SDL2.lib / SDL2_ttf.lib absents de ReleaseC1083 puis LNK2019

5PrecompiledHeader=Create sur pch.cpp conditionné à Debug|x64C1083 sur tous les fichiers

La cause 4 mérite son détail

MSVC émet, dans <yvals.h>, un #pragma detect_mismatch("_ITERATOR_DEBUG_LEVEL", …). L’éditeur de liens compare donc les deux moitiés du programme et refuse de les assembler. C’est une protection, pas un hasard — sans elle, la divergence serait silencieuse :

Type (MSVC x64)_ITERATOR_DEBUG_LEVEL = 0
(la LIB, avec NDEBUG)		_ITERATOR_DEBUG_LEVEL = 2
(l’EXE, avec _DEBUG)
std::vector<int>24 octets32 octets
std::string32 octets40 octets

Un std::vector construit côté LIB et lu côté EXE serait décalé de 8 octets. Toute la hiérarchie, tous les m_children, tous les SparseSet traversent cette frontière.

Résultat de l’étape
Cinq obstacles, dont trois invisibles tant qu’on ne lit pas le .vcxproj (1, 4, 5). Le plan devient : réparer le build d’abord, chercher les bugs ensuite — l’inverse aurait fait attribuer au moteur des défauts de configuration.
Ce que ça interdit
Toute conclusion du type « le moteur plante en Release ». À ce stade, le moteur n’a pas encore eu l’occasion de planter en Release.
Étape 2 La racine de contenu : un marqueur, trois candidats
Objectif
Remplacer une macro figée à la compilation par une résolution à l’exécution, pour que le binaire cesse de connaître l’arborescence de la machine qui l’a produit (R36).
Entrée (étape 1)
Cause n°1 : cheminProjet = PROJECT_DIR sans garde. On ne se contente pas d’ajouter la macro en Release — ce serait le contre-exemple CE-1.

Le marqueur

inline constexpr const char* kContentMarker = "engine.json";

static bool IsContentRoot(const std::filesystem::path& dir)
{
    if (dir.empty()) return false;
    std::error_code ec;
    return std::filesystem::exists(dir / kContentMarker, ec) && !ec;
}

On teste la présence du marqueur, jamais l’existence du dossier seul. Un x64\Release\ vide capterait sinon la résolution et court-circuiterait les replis suivants. C’est la même discipline que les invariants du moteur : on vérifie le fait observable, pas le raisonnement sur le fait.

Simulateur — qui gagne, et pourquoi

Résultat de l’étape
Une fonction qui renvoie un chemin ou rien, et qui journalise la liste des chemins essayés quand elle renvoie rien. Un « fichier introuvable » sans cette liste coûte une heure ; avec, trente secondes.
Décision notable
Aucun cache interne. Pas de static const auto root = … : ce serait un état global caché, initialisé à un moment que personne ne contrôle, impossible à réinitialiser dans un test, et une seconde autorité à côté d’EngineConfig. main() résout une fois, stocke, distribue.
Étape 3 ExecutableDir — et le piège de MAX_PATH
Objectif
Obtenir le dossier de l’exécutable de façon fiable, indépendamment du répertoire courant et de la manière dont le processus a été lancé.
Entrée (étape 2)
Le candidat n°2 de ResolveContentRoot a besoin de ce chemin. S’il est faux, c’est tout le scénario « binaire livré » qui tombe.

Où vivent les symboles

Core/Platform.h les rendait déjà disponibles, avec les bonnes gardes : WIN32_LEAN_AND_MEAN, NOMINMAX (sans lui, les macros min/max cassent std::clamp utilisé dans CameraZoomSystem), NOGDI (sans lui, RGB(...) entre en collision avec le type Color).

Règle R37. Un en-tête n’impose jamais à ses consommateurs les dépendances de son implémentation. D’où ContentRoot.h qui n’inclut que <filesystem> et <span>, et ContentRoot.cpp seul à inclure Platform.h.

Le contrat de retour, et pourquoi la boucle

  • Succès → nombre de wchar_t copiés, zéro final exclu. Donc succès ⟹ n < taille du buffer, toujours.
  • Buffer trop petit → renvoie exactement nSize, chaîne tronquée mais terminée, ERROR_INSUFFICIENT_BUFFER.
  • Échec → 0.

MAX_PATH vaut 260, terminaison comprise. Mais les fonctions …W ne sont pas limitées à 260 : jusqu’à 32 767 caractères. Abandonner à 260 serait un mauvais contrat — on double et on recommence.

Résultat de l’étape
Un dossier normalisé par weakly_canonical (ou le brut en cas d’échec — un chemin non normalisé reste utilisable, un chemin vide non).
Note pour plus tard
hModule = nullptr désigne le module de l’EXE du processus. Si LibraryV3 devenait un jour une DLL, il faudrait GetModuleHandleExW avec GET_MODULE_HANDLE_EX_FLAG_FROM_ADDRESS. Aujourd’hui c’est une bibliothèque statique : nullptr est exactement ce qu’on veut.

Résultat de l’étape
Zéro chemin absolu dans un fichier versionné. L’installation sur une machine neuve se résume à copier .example et à corriger trois lignes.
Contrepartie assumée
LibraryV3 ne se construit plus seul : il désigne les .props du dépôt de l’EXE. C’est une dépendance d’outillage, pas de code — aucun #include de la LIB ne pointe vers l’EXE. À remplacer par un dépôt LV3.Build ou un sous-module le jour où la LIB devra être construite isolément (point A10-12).
Étape 6 Le câblage, et la garde qui refuse de compiler sans lui
Objectif
Brancher les deux feuilles au bon endroit de la chaîne, et faire en sorte que leur absence produise une erreur nommée plutôt qu’un binaire mal réglé.
Entrée (§1)
La chaîne d’imports : nos feuilles doivent être en dernière position, après Microsoft.Cpp.$(Platform).user.props.

6a — Désigner le dossier

<!-- EXE, tout en haut, après <Project> -->
<PropertyGroup><LV3BuildDir>$(MSBuildThisFileDirectory)Build\</LV3BuildDir></PropertyGroup>

<!-- LIB -->
<PropertyGroup><LV3BuildDir>$(MSBuildThisFileDirectory)..\RefactoNouvelleLibrairieV3\Build\</LV3BuildDir></PropertyGroup>

Pourquoi pas $(SolutionDir) : cette macro n’est définie que lorsque le build passe par la solution. En ligne de commande, depuis un script ou un pipeline, elle est vide — et le Condition="exists(…)" devient faux en silence, produisant un binaire sans aucun des réglages. $(MSBuildThisFileDirectory) désigne le dossier du fichier qui contient l’expression, et vaut toujours quelque chose.

Les macros de journal, et l’erreur à ne pas refaire

// config.h — DÉFINITION. Aucun #include "Logger.h" ici.
#if LV3_DEBUG_LOG
    #define LV3_LOG_DEBUG(msg)   LV3::Logger::info(msg)
#else
    #define LV3_LOG_DEBUG(msg)   ((void)0)
#endif
// ContentRoot.cpp — APPEL. Ce fichier inclut déjà Logger.h.
LV3_LOG_DEBUG("[Content] racine = " + exeDir.string());
Règle R48. Un en-tête de configuration est une feuille de l’arbre d’inclusion : tout le monde l’inclut, il n’inclut personne du projet. Une macro qui nomme un service du moteur ne crée aucune dépendance d’en-tête — seule l’unité qui l’utilise doit inclure ce service.

Ajouter #include "Logger.h" dans config.h crée un cycle, puisque Logger.h inclut config.h. Le #pragma once n’empêche pas la boucle : il la transforme en inclusion partielle, et l’erreur apparaît très loin de sa cause — 'void LV3::Logger::info(std::string_view)' : la redéclaration du membre n’est pas autorisée, signalée dans Logger.h alors que la ligne fautive est dans config.h.

Et ici ((void)0) est le bon choix de branche éteinte, contrairement au cas de l’assertion : l’argument est une chaîne construite, pas une condition à type-vérifier — et l’on veut précisément que la concaténation std::string ne soit pas compilée, car elle coûterait une allocation par appel.

Étape 9 LV3_ASSERT affranchi de assert — et le sizeof
Objectif
Que LV3_ASSERTS_ENABLED=1 active réellement quelque chose en Release. Et, par effet de bord voulu, que les assertions soient type-vérifiées même éteintes.
Entrée (étape 8)

Le piège qui aurait rendu l’étape 8 inutile. assert de la bibliothèque standard se neutralise dès que NDEBUG est défini — ce que fait Release. Une configuration RelWithAsserts avec LV3_ASSERTS_ENABLED=1 aurait donc produit assert(x)… lui-même vide. Un commutateur qui ne commute rien.
namespace LV3
{
    // inline : vit dans config.h. fprintf et non Logger : Logger.h inclut
    // config.h, donc un cycle d’inclusion serait assuré. Un mécanisme
    // d’assertion ne doit dépendre de rien du moteur — surtout pas quand
    // le moteur va mal.
    [[noreturn]] inline void AssertFailed(const char* expr, const char* file, int line)
    {
        std::fprintf(stderr, "\n[LV3_ASSERT] %s\n  %s:%d\n", expr, file, line);
        std::fflush(stderr);
    #ifdef _MSC_VER
        __debugbreak();     // s’arrête DANS le débogueur, au bon endroit
    #endif
        std::abort();
    }
}

Pourquoi __VA_ARGS__ et pas (x)

Une expression contenant une virgule non parenthésée — LV3_ASSERT(std::min(a,b) > 0) — serait vue comme deux arguments par le préprocesseur. Avec __VA_ARGS__, elle passe. Et #__VA_ARGS__ donne à AssertFailed le texte complet de l’expression, ce qui rend l’idiome && "message" réellement utile : la chaîne vaut true, ne change pas la condition, et apparaît dans le diagnostic.

Pourquoi sizeof et pas ((void)0)

C’est le gain principal de l’étape, et il était imprévu.

((void)0) — avant((void)sizeof(!(…))) — après
Expression évaluée en Release ?nonnon
Expression compilée en Release ?nonoui
Variables de l’assertion comptées comme utilisées ?non → C4189 en cascadeoui → l’avertissement s’éteint parce que le code est correct
Membre renommé, signature changée ?invisible jusqu’au prochain build Debugerreur de compilation immédiate
Gain constaté à la première compilation. FragmentContext::magic était déclaré sous #if LV3_DEBUG, et son assertion est désormais compilée dans toutes les configurations → erreur. L’incohérence existait depuis longtemps : le champ témoin et son contrôle vivaient sur deux interrupteurs différents.
Règle R47. Une donnée qui n’existe que pour être vérifiée par une assertion partage impérativement le commutateur de cette assertion. Deux #if distincts sur un témoin et son contrôle finissent toujours par diverger — et la divergence ne se voit que dans la configuration qu’on compile le moins.
Règle R46. Une assertion n’a jamais d’effet de bord. LV3_ASSERT(++i < n) : l’expression est compilée mais jamais exécutée quand les assertions sont éteintes. Debug et Release divergent, et le bug ne se manifeste que là où on ne le cherche pas.
Résultat de l’étape
Un mécanisme d’assertion indépendant de la CRT, qui s’arrête dans le débogueur, affiche l’expression, et type-vérifie ses conditions dans toutes les configurations.
Reste à faire
Passe grep assert( : les appels directs à assert restent gouvernés par NDEBUG et resteront muets dans RelWithAsserts — une seconde autorité d’assertion (point A10-4).
Étape 10 Les gardes de la suite de tests
Objectif
Faire disparaître un LNK2001 qui n’apparaissait qu’en Release — et choisir le bon sens de correction.
Entrée (étape 9)
Zéro avertissement en Debug, mais le lien Release échoue sur LV3::Tests::TestCameraZoom.

TestCameraZoom.cpp enfermait tout son contenu dans #ifdef _DEBUG ; en Release il compile — on le voit passer dans la sortie — mais produit une unité de traduction vide. RunAllTests.cpp déclarait et appelait sans garde.

Règle R43. Une garde de compilation autour d’une définition doit avoir sa jumelle autour de chaque déclaration et de chaque appel. Une définition conditionnelle appelée inconditionnellement ne produit jamais d’erreur de compilation : elle produit une erreur d’édition de liens, à des kilomètres de la cause, et seulement dans la configuration où la condition est fausse.
Le mauvais sens de correction (CE-6). Retirer la garde de la définition « pour faire passer le lien ». Ça compile, ça lie — et on obtient en Release une fonction dont toutes les assertions ont disparu : elle parcourt ses huit sections, n’en vérifie aucune, imprime ses lignes de tableau et annonce tous les cas passent. Un test qui ne peut plus échouer est pire qu’un test absent : il produit une confiance fausse.

Et ce n’était pas un risque théorique. Les C4189 de la même compilation listaient onze variables — kEps, expectedW, s, area, before, countBefore — toutes des valeurs attendues calculées et jamais comparées. /W4 venait d’annoncer que la suite de non-régression était inerte en Release. TestCameraZoom avait au moins l’honnêteté de disparaître.

Règle R44. Un avertissement se corrige en supprimant sa cause, jamais en supprimant sa visibilité. (void)x et [[maybe_unused]] sont réservés au cas où l’inutilisation est réellement voulue et définitive.

Le cas [[nodiscard]] contre C4189

Dans TestF1_EntityVersioning, ignorer le retour de CreateEntity déclenchait C4834 ; le stocker sans l’utiliser déclenchait C4189. Il n’y avait pas d’issue syntaxique — parce que le problème ne l’était pas.

Avant — une variable pour faire taire
LV3::Entity held = reg.CreateEntity();
reg.DestroyEntity(held);
LV3::Entity Result = reg.CreateEntity();  // recycle le slot
assert(!reg.IsAlive(held));
Après — le témoin est interrogé
LV3::Entity held = reg.CreateEntity();
const std::uint32_t heldIndex = LV3::EntityIndex(held);
reg.DestroyEntity(held);

LV3::Entity recycled = reg.CreateEntity();
LV3_ASSERT(LV3::EntityIndex(recycled) == heldIndex
           && "le slot n’a pas été recyclé");
LV3_ASSERT(recycled != held);
LV3_ASSERT(!reg.IsAlive(held));
LV3_ASSERT(reg.IsAlive(recycled));

Sans la vérification du recyclage, le §4 ne prouvait rien : un Registry qui ne recyclerait jamais ses index aurait passé le test.

Règle R49. Quand [[nodiscard]] et « variable non référencée » se contredisent, ce n’est jamais un conflit de règles : c’est que la valeur a un sens que le code n’a pas encore exploité. Le [[nodiscard]] dit « regarde-moi » ; le C4189 dit « tu m’as rangée sans me regarder ». Les deux disent la même chose.
Résultat de l’étape
Lien Release réussi. Zéro erreur, zéro avertissement sur les deux projets et les deux configurations.
Point ouvert
Onky l’a relevé lui-même : « en mode release, il n’y aura plus de filet de sécurité ». Exact pour les invariants — pas pour les tests, qui n’ont rien à faire dans un binaire livré. C’est ce qui motive RelWithAsserts (A10-3).

A10-14 · Le /arch: global : décision renversée

A10 (ce lot) — aucun /arch:

Motif : un flag d’architecture global est incompatible
avec un dispatch runtime. Le SIMD devait passer par des
