Le graphe de scène : correct d’abord, rapide ensuite

Ce lot reconstruit la leçon 06 telle qu’elle s’est déroulée : un audit des deux dépôts, puis trois séances qui ont rendu le graphe de scène correct (séance 1), lui ont appris à choisir ses caméras sans les connaître par leur nom (séance 2a) et lui ont donné ses verbes de mutation (séance 2b). La partie « rapide » (traversée aplatie, constat A3) a été différée à la campagne de mesure : elle est présentée ici comme une décision en attente.

0.1 · Pourquoi ce lot

Au 1ᵉʳ septembre 2026, le moteur savait projeter, rasteriser, cadrer une caméra et charger une scène. Il ne savait pas faire tourner la scène du projet : solar_system.json. Onky utilisait SceneBasicTest.json à la place, « mais ce n’est pas le but ». La leçon 06 avait donc un fil rouge très concret : remettre le système solaire en service.

L’audit a montré que la panne avait deux causes, et aucune dans le graphe lui-même : main.cpp cherchait une caméra nommée "Top_Camera" que la scène ne contient pas (bug 46), et ParseMesh calculait un chemin résolu puis chargeait l’autre (bug 42). Mais en lisant le code du graphe pour le vérifier, l’audit a trouvé pire : un chargeur qui perd des nœuds selon l’ordre des lignes du fichier, sans un message.

Le contre-exemple de départ. « La scène s’affiche avec SceneBasicTest, donc le graphe marche. » Non. Le même chargeur, lancé sur le système solaire avec les nœuds simplement réordonnés (enfants avant parents), perd 3 nœuds sur 13 : la Lune, Phobos et Deimos. Le journal annonce pourtant « Construction de la scène terminée avec succès ». Un test qui passe sur un seul ordre de données ne prouve rien sur les autres. Le laboratoire rejoue ce cas.

Ce lot est aussi le premier où le graphe change pendant le jeu : un vaisseau qui s’arrime à une station devient son enfant, une planète détruite emporte ses lunes. Sans ces verbes, le graphe était une photo prise au chargement.

0.3 · Contexte et objectif fonctionnel

Ce qu’est un graphe de scène, côté joueur

Le joueur voit la Lune tourner autour de la Terre, qui tourne autour du Soleil. Personne n’a écrit la trajectoire de la Lune en coordonnées monde : on a écrit « la Lune est à 2 unités de la Terre » et « la Terre est à 15 unités du Soleil ». Le graphe compose ces deux phrases. C’est tout son métier : chaque nœud décrit sa position dans le repère de son parent, et le moteur en déduit la position monde de tous les nœuds, à chaque frame.

Les quatre objectifs du lot

  1. Un graphe correct quel que soit l’ordre du fichier : le chargeur est invariant par permutation des nœuds, refuse les parents inconnus, les doublons et les cycles en nommant le coupable (séance 1).
  2. Une seule définition de « racine » : dérivée du parent, plus stockée à côté (séance 1, constat A1).
  3. La scène dit quelles caméras existent, l’utilisateur choisit celle qu’il regarde : plus aucun nom de caméra dans le code (séance 2a, bug 46).
  4. Un graphe qui vit : ré-parenter, détacher, détruire un sous-arbre, sans jamais briser la symétrie parent ↔ enfants (séance 2b, constat A2).

Critère de sortie de la leçon, fixé dès l’audit : solar_system.json, l’original, charge, s’affiche et orbite en temps réel.

2 · La partie technique

Six mécanismes portent tout le lot. Aucun n’est une technique nommée de la littérature : ce sont des propriétés du C++, de l’ECS et de la géométrie qu’il faut connaître précisément, parce qu’elles échouent en silence.

2.1 · Les trois verbes d’écriture d’un stockage ECS

Un stockage de composants peut recevoir trois sortes d’écriture. Elles n’ont pas le même contrat, et EnTT leur donne trois noms :

VerbeSi absentSi présentEnTTLibraryV3
créerconstruiterreur (assert)emplaceemplaceComponent ✔
créer ou remplacerconstruitremplace toutemplace_or_replaceaddComponent — sous le nom de « créer »
modifiererreurmute en placepatch / replaceTryGet + écriture d’un champ

linkChildToParent voulait « modifier le parent de l’enfant ». Il a appelé « créer ou remplacer », et a remplacé la liste m_children que la ligne d’un enfant précédent venait de remplir. Le correctif ne touche pas addComponent : il fait choisir à l’appelant le bon verbe (TryGet puis écriture du seul champ m_parent). Le renommage addOrReplaceComponent avait été proposé en P2 ; il n’a pas été fait (roadmap L6-8).

2.2 · operator[] n’est jamais une recherche (R28)

Deux bugs du lot (41 et 48) viennent du même réflexe : écrire conteneur[clé] pour lire. Selon le conteneur, [] insère ou exige ; il ne cherche jamais. Choisis un cas :

R28. Toute recherche dont l’absence est une erreur s’écrit find() suivi d’un diagnostic qui nomme la clé. .at() est réservé aux cas où l’absence est un bug interne (exception), jamais une donnée d’auteur mal formée.

2.3 · Une racine se déduit, elle ne se stocke pas (R27)

Avec m_isRoot, le composant portait deux témoins du même fait : « je n’ai pas de parent ». Le bug 40 fabriquait déjà des états où ils divergent : Earth recevait {∅, [Moon], true} (créée comme parent de la Lune) puis {Sun-Pivot, [], false}. Dans l’autre sens d’écrasement, on aurait eu un nœud racine et enfant à la fois, propagé deux fois par frame.

Les deux surcharges vivent dans deux fichiers parce que les dépendances l’imposent :

// Component.hpp — ne connaît que la donnée ; Registry.hpp inclut ce fichier,
// donc ce fichier ne peut JAMAIS mentionner Registry (inclusion circulaire).
[[nodiscard]] constexpr bool IsRoot(const HierarchyComponent& h) noexcept
{ return h.m_parent == NULL_ENTITY; }

// Hierarchy.hpp — a le droit d'inclure Registry.hpp ; loge la CONVENTION A1 :
// pas de HierarchyComponent = racine. Délègue : la règle n'est écrite qu'une fois.
[[nodiscard]] inline bool IsRoot(const Registry& registry, Entity e)
{
    const HierarchyComponent* h = registry.TryGet<HierarchyComponent>(e);
    return !h || IsRoot(*h);
}

Règle de choix : tu tiens le composant (boucle ViewGroup<HierarchyComponent>) → IsRoot(h), aucune recherche. Tu ne tiens qu’une entité (callback ForEachAlive) → IsRoot(registry, e), une seule recherche (contre deux pour hasComponent + getComponent).

Touches

2.5 · L’invariant parent ↔ enfants, et l’ordre collecter, détacher, détruire

Deux champs portent une seule relation : child.m_parent == p si et seulement si child ∈ p.m_children. Un invariant à deux champs ne survit que derrière une API. Depuis la séance 2b, m_parent et m_children ne sont écrits que dans Hierarchy.cpp ; AttachToParent est static, donc invisible pour l’éditeur de liens hors de ce fichier.

DestroyHierarchy procède en trois temps, et l’ordre est le cœur :

  1. Collecter le sous-arbre (pré-ordre) avant toute destruction : DestroyEntity retire des composants par échange avec le dernier élément du tableau dense ; détruire en parcourant les listes qu’on lit, c’est lire un tableau qui bouge.
  2. Détacher la racine du sous-arbre, pour que le parent survivant n’ait jamais, même un instant, un handle mort dans sa liste.
  3. Détruire chaque entité collectée.

Le dépôt a depuis ajouté un temps entre 2 et 3 (bug 53, AM4) : dénouer tout le sous-arbre, pour que DestroyEntity puisse refuser toute entité encore liée.

2.6 · Changer de parent : la recette ou le résultat

Un m_local n’est pas une position : c’est une position exprimée dans la langue du parent, et cette langue contient sa translation, sa rotation et son échelle. Changer de parent sans traduire, c’est garder les mots en changeant de langue.

  • local conservé (ce que fait SetParent aujourd’hui) : garde la recette, l’objet saute. Juste pour instancier un objet sous un parent.
  • monde conservé (keepWorld, Unity : worldPositionStays = true par défaut) : garde le résultat, réécrit la recette. Juste pour un arrimage.

Dans la convention du moteur (vecteur-ligne, enfant à gauche) : Wenfant = L · Wparent, donc pour garder W : L′ = Wenfant · WnouveauParent⁻¹. Le piège est la soustraction de positions, qui n’est juste que si le nouveau parent n’est ni tourné ni mis à l’échelle :

Le vaisseau est en (8, 0) monde, enfant de Sun-Pivot (identité). Rotation autour de Y en main droite : x′ = x·cos θ + z·sin θ, z′ = −x·sin θ + z·cos θ. Calcul en double précision côté navigateur : les écarts affichés sont géométriques, pas des arrondis.

Ce qui a fait différer keepWorld : L′ sort en matrice, et m_local est un TRS. Il faut décomposer (ligne 3 = translation, normes des lignes 0 à 2 = échelle, lignes normalisées → quaternion par la méthode de Shepperd). Et si le nouveau parent a une échelle non uniforme et une rotation, son inverse introduit du cisaillement qu’aucun TRS ne représente : il faudra refuser, approcher avec avertissement, ou interdire l’échelle non uniforme sur les nœuds internes. Le paramètre existe déjà, mais refuse bruyamment (Logger::error + return false, aucune mutation) : un paramètre accepté puis ignoré mentirait à l’appelant.

2.7 · Ce qui reste lent, et pourquoi on attend (constat A3)

LocalTransformSystem parcourt le tableau dense des transforms : c’est le modèle. WorldTransformSystem, lui, descend par récursion : à chaque nœud, deux TryGet (saut sparse → dense) et la lecture d’un std::vector<Entity> alloué ailleurs. Les accès mémoire sont aléatoires, et la récursion interdit la vectorisation et le découpage en threads.

Aujourd’hui — récursion, accès dispersés
PropagateWorld(e, parentW):
  tr ← TryGet<Transform>(e)         // saut 1
  si tr : tr.world ← tr.local · parentW
  h ← TryGet<Hierarchy>(e)          // saut 2
  pour c dans h.children : PropagateWorld(c, …)
Proposé (A3) — ordre aplati, non décidé
// order[] trié parents d'abord (tri topologique),
// recalculé à chaque mutation du graphe
pour i de 0 à n−1 :
  s ← order[i].self ; p ← order[i].parent  // indices denses
  world[s] ← (p == AUCUN) ? local[s]
                          : local[s] · world[p]   // p < i : déjà calculé
Contre-exemple. Remplacer la récursion par une pile explicite. Le risque de débordement de pile disparaît, les accès aléatoires restent : le problème n’était pas la pile d’appels, c’était la localité.

Décision du carnet de route : A3 attend les chiffres de la campagne de mesure (phase 4). On ne paie pas 2 à 3 séances pour un système dont on ne connaît pas le coût. Le pendant vectorisé du produit de matrices, seule boucle de calcul du graphe, est donné à l’étape 9.

Étape 9 La boucle de calcul du graphe : local · parentWorld

Objectif. Connaître exactement le calcul que PropagateWorld fait par nœud, et son pendant vectorisé, pour le jour où A3 sera décidé. Ce code n’a pas été modifié par le lot.

Produit
m_worldMatrix du nœud : ligne i = Σk local[i][k] · parent.ligne[k].
Scalaire (row-major, vecteur-ligne)
// r = a · b : chaque LIGNE de r est une combinaison
// des 4 lignes de b, pondérée par la ligne de a.
// Ordre d'addition figé : ((k0 + k1) + k2) + k3.
for (int i = 0; i < 4; ++i)
    for (int j = 0; j < 4; ++j)
        r[i][j] = ((a[i][0] * b[0][j]
                  + a[i][1] * b[1][j])
                  + a[i][2] * b[2][j])
                  + a[i][3] * b[3][j];
// 64 mul + 48 add, scalaires
Vectorisé (SSE, une ligne par registre)
#include <immintrin.h>
// b est row-major : chaque ligne b[k] = 4 floats contigus.
const __m128 b0 = _mm_loadu_ps(b[0]);   // b0 = [b00 b01 b02 b03]
const __m128 b1 = _mm_loadu_ps(b[1]);
const __m128 b2 = _mm_loadu_ps(b[2]);
const __m128 b3 = _mm_loadu_ps(b[3]);
for (int i = 0; i < 4; ++i)
{
    // diffuse a[i][k] dans les 4 couloirs, multiplie la ligne b[k]
    __m128 r = _mm_mul_ps(_mm_set1_ps(a[i][0]), b0);          // k0
    r = _mm_add_ps(r, _mm_mul_ps(_mm_set1_ps(a[i][1]), b1));  // + k1
    r = _mm_add_ps(r, _mm_mul_ps(_mm_set1_ps(a[i][2]), b2));  // + k2
    r = _mm_add_ps(r, _mm_mul_ps(_mm_set1_ps(a[i][3]), b3));  // + k3
    _mm_storeu_ps(out[i], r);   // ligne i de r, 4 couloirs = 4 colonnes j
}
// 16 mul + 12 add vectoriels ; mêmes opérations que le
// scalaire, même ordre → résultat identique au bit (sans FMA).

Variante AVX2 (deux lignes par registre 256 bits). Le couloir bas porte la ligne i, le haut la ligne i+1 ; on duplique chaque ligne de b dans les deux moitiés :

const __m256 B0 = _mm256_broadcast_ps(reinterpret_cast<const __m128*>(b[0]));  // [b0 | b0]

    __m256 r = _mm256_mul_ps(_mm256_set_m128(_mm_set1_ps(a[i+1][0]), _mm_set1_ps(a[i][0])), B0);
    r = _mm256_add_ps(r, _mm256_mul_ps(_mm256_set_m128(_mm_set1_ps(a[i+1][1]), _mm_set1_ps(a[i][1])), B1));
    r = _mm256_add_ps(r, _mm256_mul_ps(_mm256_set_m128(_mm_set1_ps(a[i+1][2]), _mm_set1_ps(a[i][2])), B2));
    r = _mm256_add_ps(r, _mm256_mul_ps(_mm256_set_m128(_mm_set1_ps(a[i+1][3]), _mm_set1_ps(a[i][3])), B3));

Étape 11 Les verbes : Detach, SetParent, DestroyHierarchy (constat A2)

Objectif. Que le graphe puisse changer pendant le jeu sans jamais briser l’invariant parent ↔ enfants, et qu’une mutation refusée laisse le graphe exactement comme elle l’a trouvé.

Reçoit

Produit
Quatre portes publiques ; m_children écrit uniquement dans Hierarchy.cpp.
void Detach(Registry& registry, Entity child)
{
    HierarchyComponent* hc = registry.TryGet<HierarchyComponent>(child);
    if (!hc || hc->m_parent == NULL_ENTITY) return;            // détacher une racine : no-op
    if (HierarchyComponent* ph = registry.TryGet<HierarchyComponent>(hc->m_parent))
    {
        auto& kids = ph->m_children;
        const auto it = std::find(kids.begin(), kids.end(), child);
        LV3_ASSERT(it != kids.end() && "Invariant parent<->children brisé : écriture directe quelque part");
        if (it != kids.end()) { *it = kids.back(); kids.pop_back(); }   // swap-erase
    }
    hc->m_parent = NULL_ENTITY;
}

bool SetParent(Registry& registry, Entity child, Entity newParent, bool keepWorld)
{
    if (keepWorld)  { Logger::error("SetParent — keepWorld : pas encore implémenté"); return false; }
    if (child == newParent) { Logger::error("SetParent — propre parent"); return false; }
    if (newParent != NULL_ENTITY && IsDescendantOf(registry, newParent, child))
    { Logger::error("SetParent — cycle refusé"); return false; }
    Detach(registry, child);
    if (newParent != NULL_ENTITY) AttachToParent(registry, child, newParent);
    return true;
}

void DestroyHierarchy(Registry& registry, Entity root)
{
    std::vector<Entity> subtree;
    CollectSubtree(registry, root, subtree);   // 1. collecter (pré-ordre, root inclus)
    Detach(registry, root);                    // 2. le parent survivant oublie le mort
    // (dépôt, bug 53) 2b. dénouer : m_parent ← ∅, m_children.clear() sur tout le sous-arbre
    for (Entity e : subtree)
        registry.DestroyEntity(e);             // 3. chaque storage nettoie sa part
}

Pourquoi linkChildToParent délègue à AttachToParent et pas à SetParent. On délègue vers le bas (le geste nu), jamais vers le haut (le geste + les gardes d’un autre contrat) : la construction paierait sinon un Detach et une remontée O(profondeur) par nœud chargé, pour des garanties qu’elle possède déjà.

Pourquoi le swap-erase. erase(it) décalerait le vecteur pour préserver un ordre des frères dont personne ne dépend. Si un jour quelque chose en dépend (ordre de dessin d’une interface), ce sera une décision explicite.

Points relevés dans le dépôt (déjà au carnet de route, phase 2) : IsDescendantOf n’a pas de compteur de pas (boucle infinie sur un graphe déjà cyclique, que le bug L6-1 laisse passer) ; CollectSubtree et IsDescendantOf ont une liaison externe sans déclaration dans Hierarchy.hpp.

Pendant vectorisé : sans objet (mutations ponctuelles ; std::find sur une liste de frères de quelques éléments).
