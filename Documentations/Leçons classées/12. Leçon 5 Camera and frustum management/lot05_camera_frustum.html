Dette & roadmap

0Pourquoi ce lot

On vient de faire tourner un rasterizer : il sait remplir un triangle dont on lui donne les trois sommets en pixels. Mais personne, dans le moteur, ne sait encore produire ces pixels à partir d'une scène 3D.

La question n'est pas « comment dessiner un triangle » — c'est réglé. La question est : quel triangle, vu d'où, et lequel ne pas dessiner du tout.

Le constat qui déclenche ce lot

Un triangle de la scène ne devient des pixels que s'il franchit trois épreuves successives :

  1. il existe un point de vue — une position, une orientation, un objectif ;
  2. il tombe dans le cône de vision de ce point de vue ;
  3. il se trouve devant ce qui a déjà été dessiné.

Ces trois épreuves sont le sujet du lot. Elles n'ont rien d'esthétique : ce sont elles qui déterminent si l'écran affiche quelque chose, et surtout — pour un moteur CPU — ce qu'on s'épargne de calculer.

La vraie motivation

Sur une scène normale, 90 % de la géométrie est invisible : derrière la caméra, hors du champ, trop loin, ou masquée. Un moteur CPU qui transforme tout avant de s'en apercevoir travaille dix fois trop. Le frustum n'est pas un raffinement graphique, c'est le filtre qui rend le rendu logiciel réaliste.

Et il y a une raison de l'aborder maintenant, avant d'aller plus loin dans le rasterizer : deux décisions de ce lot — le sens du repère et la façon de coder la profondeur — déterminent le sens de parcours des triangles et le fonctionnement du Z-buffer. Les trancher après, c'est réécrire le rasterizer.

Le point de départ réel

Le code dont part ce lot n'est pas vierge : c'est une classe Camera de 400 lignes et une classe Frustum de 700, héritées de LibV2. Elles fonctionnaient. Elles n'étaient pas récupérables — on verra pourquoi en §4, et le relevé complet des 18 bugs trouvés en §13.

2Contexte et objectif fonctionnel

Avant toute matrice : qu'est-ce que l'utilisateur du moteur doit pouvoir faire à la fin de ce lot qu'il ne pouvait pas faire avant ?

Les trois capacités visées

1. Poser une caméra dans la scène, et la déplacer librement.
Une caméra est une entité de la scène, décrite dans le JSON comme n'importe quelle autre. On lui attache un objectif (champ de vision, plans de coupe) et un comportement — FPS au clavier/souris, ou suivi d'une cible avec lissage. Changer de comportement = activer un composant, sans toucher une ligne du rendu.

2. Ne dessiner que ce qui est visible.
Le moteur doit répondre, par objet et pour un coût négligeable : dedans, dehors, ou à cheval. Les trois réponses, pas deux — la troisième est ce qui permettra plus tard d'éviter le clipping sur les objets entièrement visibles.

3. Afficher plusieurs points de vue simultanément.
Écran splitté, minimap, incrustation : plusieurs caméras, plusieurs régions d'écran, un seul buffer de pixels. Si l'architecture est juste, ça doit coûter un appel de plus, pas une refonte.

Le scénario de validation

Le lot est terminé quand ceci fonctionne, sans code spécifique au cas :

Fenêtre 1600 × 900, UNE texture, UN Z-buffer.

  Moitié gauche  → caméra qui suit la Terre      (fov 45°, rendu plein)
  Moitié droite  → caméra fixe du système entier (fov 60°, fil de fer)

Les deux moitiés ont leur propre matrice de vue, leur propre
projection, leur propre frustum — et ne cullent donc pas les
mêmes objets.

3Schéma dynamique d'introduction

Comprendre la méthode en la voyant, avant d'ouvrir une seule ligne de code. Tout ce qui suit dans ce document est recalculé en direct depuis ces réglages — y compris les nombres des 13 étapes.

À gauche : la scène vue de dessus (plan XZ). La caméra regarde vers -Z, conformément au repère main droite. Glisse la caméra à la souris.
À droite : la même scène après V·P puis division par w. La pyramide de vision y devient une boîte — c'est tout l'intérêt de l'espace de clip.

Objetcentre mondedist. œil p-vertex · plan critiquen-vertexétat

Ce que le schéma rend évident

Pousse near vers 12 → les objets proches basculent en Outside. Le plan near n'est pas un détail numérique : c'est une paroi qui coupe vraiment.

Décoche Reverse-Z → regarde la colonne verticale du panneau NDC s'inverser. Les objets lointains se tassent vers le haut au lieu du bas. La géométrie monde, elle, n'a pas bougé d'un pixel : seule la façon de coder la profondeur change.

Coche Far infini → le frustum n'a plus que 5 plans, et plus aucun objet ne sort par l'arrière.

Coche objet derrière l'œil puis /w avant le test → l'objet réapparaît en miroir du bon côté de l'écran. C'est le bug du « triangle qui explose quand on recule dedans », reproduit en direct. Il justifie à lui seul l'étape 9.

4L'algorithme : avant / après

L'ancien pipeline fonctionnait. Comparons-le au nouveau avant d'entrer dans le détail : les différences ne sont pas cosmétiques, chacune corrige un défaut nommé.

Avant — LibV2
  1. viewMatrix = Camera::SetViewMatrix()
    lookAt ET quaternion → double orientation
  2.   ↳ (rotation * viewMatrix).inverse()
    Gauss-Jordan 4×4 par frame
  3. projMatrix = Frustum::setProjectionMatrixV2()
    OpenGL [-1,1], sans argument, mute un membre
  4. vp = viewMatrix * projMatrix
  5. Frustum_ExtractPlan(vp)
    plan near en forme D3D sur une matrice GL → faux
  6. par mesh : calculateWorldAABB(...)
    8 points transformés puis ré-englobés
  7.   isAABBVisible(...) → bool
    2 états : l'information « entièrement dedans » est perdue
  8. invModelMatrix = modelMatrix.inverse()
  9. camPos → espace objet
  10. par face : backface en espace objet
    normale + produit scalaire par face
  11. TransformLocalMesh(poly, model)
    écrit xtransf/ytransf dans le mesh partagé
  12. Clip3DAndProject(poly, …, vp)
    clippe 6 plans en espace monde
Après — LV3
  1. view = world.inverseRigid()
    une seule orientation, inverse analytique
  2. proj = Projection::Perspective(fovY, aspect, n, f)
    fonction pure, [0,1] reverse-Z
  3. vp = view * proj
  4. frustum.Build(vp, reverseZ, infiniteFar)
    étiquettes near/far échangées en reverse-Z
  5. par mesh : AABB.Transformed(model)
    méthode centre/extent : 9 multiplications
  6.   frustum.Classify(...) → 3 états
    Inside / Intersect / Outside
  7. mvp = model * view * proj
    une seule matrice, une seule passe sur les sommets
  8. par face : clip[k] = MulRow(mvp, v[k])
  9. si un w ≤ near → rejet
    avant toute division : plus de miroir
  10. ndc = clip / w  ·  raster = viewport.ToRaster(ndc)
  11. backface = signe de EdgeFunction
    gratuit : l'aire sert déjà aux barycentriques
  12. renderer.DrawTriangle(Triangle2D, color)
    soumission ; le rendu décide du reste

Le changement n°6 n'est pas une optimisation

TransformLocalMesh écrivait les sommets transformés dans poly->Vertex(i)->xtransf — c'est-à-dire dans le mesh lui-même. Deux entités partageant le même MeshHandle s'écrasaient mutuellement, et toute parallélisation de l'étage géométrie était structurellement impossible. Ce n'est pas un gain de cycles, c'est une correction.

5Les règles — comment ça fonctionne

Maintenant la technique. Six règles structurent tout le lot ; les étapes qui suivent ne font que les appliquer.

Règle 1 — « La caméra » n'existe pas

Il n'y a pas d'objet caméra. Il y a quatre choses distinctes qui ne se connaissent presque pas. Le composant Camera d'Unity ne contient aucune position : si on veut savoir où est la caméra, on demande à son Transform, comme pour n'importe quel objet.

Le défaut du legacy

L'ancienne classe Camera portait huit représentations concurrentes d'une seule orientation : Yaw/Pitch/Roll, theta/phi, script3D[], rotationAngle, camera_rotation, rotation_mat, forward/right/UP, TO. Aucune n'était la source de vérité.

Règle 2 — La caméra ne bouge jamais, c'est le monde qui bouge

Le rasterizer ne sait projeter que depuis l'origine, le long d'un axe fixe. On ne déplace donc pas l'œil : on déplace la scène en sens inverse.

View = inverse(WorldMatrix_camera)

Et comme c'est une ISOMÉTRIE, cet inverse est analytique :

    View = [ Rᵀ | −Rᵀ·t ]        jamais un Gauss-Jordan

Règle 3 — Le pipeline des espaces

Local—M→ Monde—V→ Vue—P→ Clip—/w→ NDC—viewport→ Raster
  • On cull dans le monde, on clippe dans le clip. Le nom de l'espace le dit.
  • La division par w arrive après le clipping, jamais avant.
  • Le flip Y n'existe qu'à la dernière flèche, dans Viewport::ToRaster(). Nulle part ailleurs.

Pourquoi clipper en espace de clip — trois raisons, par ordre d'importance :

  1. La correction. Un sommet derrière l'œil a w < 0. Diviser avant de clipper inverse le signe : le point traverse l'écran et réapparaît en miroir. (coche les deux derniers interrupteurs du §3 pour le voir)
  2. Le coût. En clip space les six plans sont canoniques : -w ≤ x ≤ w, 0 ≤ z ≤ w. Une comparaison de deux flottants, contre trois multiplications par plan et par sommet en espace monde.
  3. L'universalité. Perspective, orthographique, projection oblique, far infini : les plans canoniques ne changent jamais.

Le secret industriel

Dans un rasterizer professionnel, seul le plan near impose un vrai clipping. Les quatre plans latéraux se traitent par scissor sur la bounding box du triangle, avec une guard band au-delà de laquelle seulement on clippe. Sur une scène normale, plus de 99 % des triangles ne sont jamais découpés.

Règle 5 — La matrice source décide de l'espace des plans

On n'obtient pas les plans depuis les 8 coins : on les extrait de la matrice (Gribb-Hartmann). Aucun cas particulier, normales vers l'intérieur par construction, pas de vecteurs forward/right/up à maintenir — donc pas de dégénérescence quand on regarde à la verticale.

Renderer n'est pas « une fonction qui dessine » : c'est le propriétaire de l'état de rendu. Tant qu'il était sans état, il n'était qu'un switch déguisé et paraissait inutile. Une fois qu'il détient les cibles, le viewport et le mode, le mode d'affichage devient un état, pas un argument de dessin — et l'écran splitté coûte un appel de plus.

6NDC et reverse-Z — la décision qui coûte deux coefficients

Le mot « NDC » recouvre deux notions selon la source. Levons l'ambiguïté avant d'entrer dans les étapes, parce que deux coefficients de matrice en dépendent.

X et Y : [-1,+1], sans débat

  1. Le frustum est symétrique autour de l'axe de visée → les termes de décentrement s'annulent.
  2. Le clipping devient trivial : -w ≤ x ≤ w.
  3. La précision du flottant est maximale au centre de l'écran, là où l'œil regarde.

Z : c'est là que se joue le débat

OpenGL produit [-1,1], puis répare avec glDepthRange. Direct3D, Vulkan et Metal produisent [0,1] directement — une opération affine en moins, et surtout la conversion d'OpenGL arrive trop tard.

Le chiffre qui tranche

Nombre de valeurs float distinctes dans une tranche de 0,001 :

IntervallePas du flottantValeurs distinctes
[0 ; 0,001]jusqu'à 1e-45≈ 1 000 000 000
[0,999 ; 1,0]5,96e-8≈ 16 800
[-1,0 ; -0,999]5,96e-8≈ 16 800

Facteur 60 000. En [0,1], une extrémité de la plage tombe dans la zone au milliard de valeurs — le reverse-Z l'y place au far, là où la projection en 1/z est la plus écrasée. Les deux non-linéarités se compensent. En [-1,1], les deux extrémités sont grossières : le reverse-Z y est impossible, inverser ne déplace rien.

Le gain mesuré

Incertitude sur la distance réelle représentée par un seul pas de flottant (n = 0,1, f = 1000) :

La règle à retenir

[-1,1] sur X et Y, parce que le frustum est symétrique. [0,1] sur Z, parce que le flottant ne l'est pas.
OpenGL lui-même a fait marche arrière : glClipControl(GL_LOWER_LEFT, GL_ZERO_TO_ONE) (GL 4.5, 2014) existe uniquement pour permettre le [0,1]. Vulkan n'offre même plus le [-1,1].

Scratchapixel n'a pas tort

Il enseigne le pipeline OpenGL, correctement, dans une leçon dont le sujet est la géométrie de la projection — pas l'ingénierie de la précision du Z-buffer. Il emploie d'ailleurs [0,1] pour X et Y dans sa leçon Pinhole Camera et [-1,1] dans sa leçon Projection Matrix. Le legacy LibV2 contenait littéralement les deux conventions dans le même fichier — d'où la confusion.

Les étapes, pas à pas

Treize étapes, du point de vue jusqu'au pixel. Tous les nombres affichés sont recalculés en direct depuis les réglages du §3, en float32 — Math.fround() à chaque opération, comme le CPU. Remonte modifier un curseur et redescends : les valeurs auront changé.

Convention rappelée

Row-major m[r][c], vecteur-ligne v' = v·M, translation en ligne 3, composition S·R·T, main droite (l'avant est -Z), NDC x,y ∈ [-1,+1] et z ∈ [0,1] reverse-Z.

//   M   = [ R | 0 ]        M⁻¹ = [  Rᵀ   | 0 ]
//         [ t | 1 ]              [ -t·Rᵀ | 1 ]
Matrix44 inverseRigid() const noexcept
{
    Matrix44 r;
    r.x[0][0]=x[0][0]; r.x[0][1]=x[1][0]; r.x[0][2]=x[2][0];   // transposée 3x3
    r.x[1][0]=x[0][1]; r.x[1][1]=x[1][1]; r.x[1][2]=x[2][1];
    r.x[2][0]=x[0][2]; r.x[2][1]=x[1][2]; r.x[2][2]=x[2][2];

    r.x[3][0] = -(x[3][0]*r.x[0][0] + x[3][1]*r.x[1][0] + x[3][2]*r.x[2][0]);
    r.x[3][1] = -(x[3][0]*r.x[0][1] + x[3][1]*r.x[1][1] + x[3][2]*r.x[2][1]);
    r.x[3][2] = -(x[3][0]*r.x[0][2] + x[3][1]*r.x[1][2] + x[3][2]*r.x[2][2]);

Le couloir 3 est inutilisé : c'est le prix d'une matrice 4×4 traitée en registres de 4 flottants. On le récupérera en traitant 4 objets à la fois plutôt qu'une matrice.

Contre-exemple — l'appliquer à une matrice avec échelle

inverseRigid transpose le bloc 3×3. Si ce bloc contient une échelle s, la transposée vaut s·Rᵀ et le produit donne s²·I au lieu de I :

M = scale(2) · rotateY(0.5) · translate(1,2,3)

M · M.inverseRigid()  →  diag(4, 4, 4, 1)      ❌  PAS l'identité
M · M.inverse()       →  diag(1, 1, 1, 1)      ✅

La TNR §6.3 verrouille cette limite en assertant que inverseRigid échoue en présence d'échelle. Un test qui vérifie qu'une fonction ne marche pas est un test qui documente un contrat.

// Maths/Projection.cpp — namespace LV3::Projection
Matrix44f PerspectiveOffCenter(float l, float r, float b, float t,
                               float n, float f) noexcept
{
    Matrix44f m = Zeroed();              // /!\ PAS l'identité : m[3][3] doit valoir 0

    m[0][0] =  (2.0f * n) / (r - l);
    m[1][1] =  (2.0f * n) / (t - b);
    m[2][0] =  (r + l) / (r - l);        // décentrement horizontal
    m[2][1] =  (t + b) / (t - b);        // décentrement vertical
    m[2][2] =  n / (f - n);              // ← REVERSE-Z
    m[2][3] = -1.0f;                     // recopie -z dans w (main droite)
    m[3][2] =  (n * f) / (f - n);        // ← REVERSE-Z
    m[3][3] =  0.0f;                     // matrice projective
    return m;
}

Matrix44f Perspective(float fovYRad, float aspect, float n, float f) noexcept
{
    const float t = std::tan(fovYRad * 0.5f) * n;
    const float r = t * aspect;
    return PerspectiveOffCenter(-r, r, -t, t, n, f);   // cas symétrique
}

Règle de profilage

Ce qui se calcule une fois par frame ne se vectorise pas : on le met en cache. Ce qui se calcule une fois par pixel se vectorise. Entre les deux, on mesure.

4
Extraction des 6 plans — Gribb-Hartmann
Objectif Obtenir les six plans du volume de vision en espace monde, directement depuis V·P. Pas de trigonométrie, pas de vecteurs à maintenir, pas de cas particulier : perspective, orthographique, far infini — les mêmes quinze lignes.

Le raisonnement en une phrase

Un point est dans le volume canonique si -w ≤ x ≤ w, -w ≤ y ≤ w et 0 ≤ z ≤ w. Chacune de ces six inégalités est une combinaison linéaire des composantes du clip — donc un plan. Et comme clip.j = Σᵢ vᵢ·M[i][j], c'est la colonne j de V·P qui porte le composant j.

void Frustum::Build(const Matrix44f& M, bool reverseZ, bool infiniteFar) noexcept
{
    auto col = [&M](int j){ return Plane(Vec3f(M[0][j], M[1][j], M[2][j]), M[3][j]); };
    auto add = [](const Plane& a, const Plane& b){ return Plane(a.normal+b.normal, a.d+b.d); };
    auto sub = [](const Plane& a, const Plane& b){ return Plane(a.normal-b.normal, a.d-b.d); };

    const Plane cx = col(0), cy = col(1), cz = col(2), cw = col(3);

    m_planes[Left]   = add(cw, cx);      //  x + w ≥ 0
    m_planes[Right]  = sub(cw, cx);      //  w − x ≥ 0
    m_planes[Bottom] = add(cw, cy);      //  y + w ≥ 0
    m_planes[Top]    = sub(cw, cy);      //  w − y ≥ 0

    // NDC z ∈ [0,1] : les deux conditions sont (z ≥ 0) et (w − z ≥ 0).
    //   standard  → z ≥ 0 est le NEAR
    //   reverse-Z → z ≥ 0 est le FAR      ... on échange les étiquettes.
    if (reverseZ) { m_planes[Near] = sub(cw, cz); m_planes[Far] = cz;          }
    else          { m_planes[Near] = cz;          m_planes[Far] = sub(cw, cz); }

    // Far infini : la colonne z donne une normale nulle → plan dégénéré.
    // (Far est le DERNIER de l'enum : c'est ce qui rend la troncature possible.)
    m_count = infiniteFar ? int(Far) : int(PlaneCount);

    for (int i = 0; i < m_count; ++i) m_planes[i].Normalize();
}

{

    // Garde ANTI-DIVISION uniquement : seul le zéro véritable est rejeté.
    // Cas légitime : plan Far dégénéré quand far = infini.
    if (len2 > NEAR_ZERO_SQ)                   // 1e-30, PAS une tolérance géométrique

La règle qui en sort

Une tolérance géométrique (« ce point est-il sur le plan ? ») et une garde anti-division (« ce dénominateur est-il nul ? ») sont deux constantes différentes, à trois ordres de grandeur l'une de l'autre. Les confondre est une erreur silencieuse.

FrameBuffer décrit la mémoire ; Viewport décrit la région qu'on y dessine. Ils coïncident 99 % du temps — c'est le 1 % restant qui justifie la séparation : écran splitté, minimap, incrustation, letterboxing, faces de cubemap. Backface culling — gratuit
Objectif Éliminer les faces qui tournent le dos à la caméra — la moitié de la géométrie d'un objet fermé. Et le faire sans rien calculer de nouveau : l'aire signée sert déjà à normaliser les coordonnées barycentriques.
Entrée — le triangle en pixels
Résultat — aire signée
// Rendering/Rasterizer.h — un NOYAU scalaire, deux gabarits.
// La fonction d'arête ne travaille QUE sur x et y : le z n'intervient jamais.
// Trois services pour le prix d'un :
//   * sur trois sommets   -> deux fois l'aire signée (backface + normalisation)
//   * signe sur un pixel  -> le pixel est-il du bon côté de l'arête
//   * valeur / aire       -> coordonnée barycentrique
[[nodiscard]] LV3_FORCEINLINE constexpr float EdgeFunction(
    float ax, float ay, float bx, float by, float px, float py) noexcept
{
    return (bx - ax) * (py - ay) - (by - ay) * (px - ax);
}

template<typename V>   // marche pour Vec2f comme pour Vec3f
[[nodiscard]] LV3_FORCEINLINE float EdgeFunction(const V& a, const V& b, const V& c) noexcept
{ return EdgeFunction(a.x, a.y, b.x, b.y, c.x, c.y); }

// Appel, dans RenderView :
if (EdgeFunction(r[0], r[1], r[2]) <= 0.0f) continue;   // backface

Les quatre règles transposables qui en sortent

1. Une constante absolue appliquée à une grandeur relative est une bombe à retardement. EdgeFunction = |arête| × distance : exiger w ≥ 1 revient à exiger distance ≥ 1/|arête| — 0,0025 px sur un triangle de 400 px, 0,33 px sur un de 3 px. Symptôme : un échec qui disparaît quand la taille augmente.

2. inline ⇒ le corps va dans le .h. Une fonction inline n'émet aucun symbole externe : sa définition doit être visible dans chaque unité de compilation qui l'appelle.

3. Un seul type de contexte derrière un void*. static_cast<T*>(void*) réussit toujours. Le compilateur ne vérifie rien ; c'est à la conception de le faire.

4. Un fichier appartient à la couche de son argument le plus haut. Projection ignore Camera, Frustum ignore Mesh, Renderer ignore le Registry. Test : « si je remplaçais SDL par Win32 GDI, ce fichier changerait-il ? »
