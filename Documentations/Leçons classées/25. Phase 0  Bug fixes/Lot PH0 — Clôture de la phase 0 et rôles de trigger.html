0.3 · Contexte et objectif fonctionnel

Ce que fait un trigger, côté joueur

Un trigger est une sphère invisible attachée à une entité. Quand le vaisseau du joueur entre dans la couronne solaire, le jeu doit le savoir une fois (début des dégâts, son de grésillement), le savoir à chaque frame tant qu’il y reste (dégâts continus), et le savoir quand il en sort (fin du son). Ce sont les trois transitions ENTER, STAY et EXIT. Le système de triggers ne fait pas de physique : il ne repousse rien, il signale.

Deux sortes d’objets portent un trigger, et ils n’ont pas le même rôle :

  • une zone est un lieu : la couronne du Soleil, l’atmosphère de Vénus, la ceinture d’astéroïdes, la zone de ravitaillement autour de la Terre. Elle décrit ce qui arrive à celui qui y entre ;
  • une sonde (probe) est ce qui traverse les lieux : le vaisseau.

Deux zones qui se recouvrent dans l’espace (l’atmosphère de la Terre et sa zone de gravité) ne « s’entrent » pas l’une dans l’autre. Ça n’a pas de sens de jeu. Seule une paire zone/sonde produit un événement.

Les quatre objectifs du lot

  1. Zéro allocation par frame dans TriggerSystem, une fois la scène chargée, sans plafond arbitraire sur le nombre de recouvrements (0.1).
  2. Des outils de debug qui ne s’imposent pas : le dump de hiérarchie existe, mais ne tourne que si on le demande (0.2).
  3. Une configuration optimisée avec filets, RelWithAsserts, où les invariants restent actifs sans le reste de l’outillage (0.3).
  4. Des rôles respectés : seule une paire zone/sonde est testée et peut publier un événement (bug 62).

2 · La partie technique

Quatre mécanismes portent tout le lot. Aucun n’est une technique nommée de la littérature : ce sont des propriétés du C++ et de MSBuild qu’il faut connaître précisément, parce qu’elles échouent en silence quand on les connaît à moitié.

2.1 · Un conteneur dans un composant chaud

Un composant « chaud » est lu ou écrit à chaque frame par un système. La règle de la leçon 03 dit qu’il doit être un POD : des valeurs posées côte à côte, copiables par memcpy, rangées dans le tableau dense du SparseSet. TriggerComponent était l’exception : il contenait un std::set<Entity>.

Le vecteur n’est pas devenu un POD : TriggerComponent porte encore trois std::string et un std::vector. Ce qui a changé, c’est le régime d’allocation. La règle n’est pas « jamais de conteneur », c’est « jamais d’allocation par frame ». Un conteneur dont la capacité ne redescend jamais la respecte une fois le pic atteint.

Règle proposée PH0.a (non actée). Un conteneur dynamique est toléré dans un composant chaud ou un tampon de système seulement si sa capacité est conservée d’une frame à l’autre (clear(), jamais de reconstruction ni de shrink_to_fit). Un plafond fixe n’est acceptable que si la cardinalité est bornée par construction, pas par observation.

Le tampon de travail newOverlaps est déclaré static dans la fonction. Il vit donc toute la durée du programme et sa capacité ne retombe jamais. Le prix : TriggerSystem n’est pas réentrant et n’est pas sûr en multithread. Ce n’est pas un problème aujourd’hui (la boucle est mono-thread) ; le commentaire du code le dit, et la roadmap le note (PH0-15).

2.2 · L’agrégat et l’ordre positionnel

TriggerComponent n’a aucun constructeur déclaré : c’est un agrégat. emplaceComponent<T>(entity, args…) le construit par std::construct_at(p, args…), ce qui, pour un agrégat, est une initialisation par liste parenthésée (C++20, P0960) : le premier argument va au premier membre, le deuxième au deuxième, et ainsi de suite. Aucun nom n’est vérifié. Seuls les types le sont.

Conséquence : le site d’appel (Serializer.cpp) et la déclaration (Component.hpp) forment un seul contrat, écrit dans deux fichiers. Ce que le compilateur fait quand ce contrat est rompu dépend de l’endroit où l’on ajoute un membre. Choisis un cas :

2.3 · Les commutateurs, et une macro qui change la forme d’un type

Un commutateur de compilation (#if LV3_ASSERTS_ENABLED) retire du code. Quand ce code est une instruction, l’effet est local. Quand c’est un membre de struct, la macro change la taille et la disposition du type. Si deux unités de compilation voient deux valeurs différentes, elles ne parlent plus du même type, sous le même nom. C’est une violation de l’ODR (One Definition Rule, [basic.def.odr]) : comportement indéfini, sans diagnostic obligatoire.

FragmentContext (Rendering/Fragment.h) est un tel type : son premier membre magic n’existe que sous LV3_ASSERTS_ENABLED. Choisis une configuration et l’endroit où la macro est définie :

Règle proposée PH0.b (non actée). Une macro qui modifie la forme d’un type déclaré dans un en-tête partagé (membre conditionnel, signature conditionnelle) se définit à un seul endroit, lu par tous les projets qui incluent cet en-tête : config.h pour la valeur par défaut, LV3.Common.props pour une surcharge par configuration. Jamais dans les propriétés d’un seul projet.

// PROPOSÉ — Scene/TriggerNarrow8.h (n'existe pas dans le dépôt)
struct ZoneLanes
{
    SimdVector<float> x, y, z, r;    // SoA, taille = multiple de 8 (bourrage : x = y = z = 0, r = -inf)
    std::vector<Entity> entity;       // zones réelles, dans l'ordre DENSE de la vue
};

// Écrit dans 'hits' les indices des zones recouvertes par la sonde, par ordre croissant.
inline void ProbeVsZones8(const ZoneLanes& zl, const Vec3f& p, float pr,
                          std::vector<uint32_t>& hits) noexcept
{
    // La sonde est la même pour les 8 couloirs : on diffuse ses 4 valeurs UNE fois.
    const __m256 px8 = _mm256_set1_ps(p.x);
    const __m256 py8 = _mm256_set1_ps(p.y);
    const __m256 pz8 = _mm256_set1_ps(p.z);
    const __m256 pr8 = _mm256_set1_ps(pr);

    for (size_t i = 0; i < zl.x.size(); i += 8)
    {
        // dx = sonde − zone, couloir par couloir : MÊME sens que pos1 − pos2 quand T1 = sonde.
        const __m256 dx = _mm256_sub_ps(px8, _mm256_load_ps(zl.x.data() + i));
        const __m256 dy = _mm256_sub_ps(py8, _mm256_load_ps(zl.y.data() + i));
        const __m256 dz = _mm256_sub_ps(pz8, _mm256_load_ps(zl.z.data() + i));

        // norm() = (x*x + y*y) + z*z — MÊME parenthésage que Vec3f::norm().
        // Ni FMA (/fp:precise l'interdit déjà), ni réassociation : sinon le dernier bit change.
        const __m256 d2 = _mm256_add_ps(_mm256_add_ps(_mm256_mul_ps(dx, dx),
                                                      _mm256_mul_ps(dy, dy)),
                                        _mm256_mul_ps(dz, dz));

        // vsqrtps : racine arrondie au plus proche (IEEE 754), identique à std::sqrt(float).
        // Surtout pas _mm256_rsqrt_ps : approximation à 12 bits, décisions différentes.
        const __m256 d = _mm256_sqrt_ps(d2);

        // s = r_sonde + r_zone (commutatif au bit près). Bourrage : r = -inf → s = -inf.
        const __m256 s = _mm256_add_ps(pr8, _mm256_load_ps(zl.r.data() + i));

        // _CMP_LT_OQ : « inférieur », FAUX si un opérande est NaN — comme le '<' scalaire.
        // Couloir de bourrage : d < -inf est faux, il ne sort jamais.
        uint32_t m = uint32_t(_mm256_movemask_ps(_mm256_cmp_ps(d, s, _CMP_LT_OQ)));

        // Un bit par zone recouverte. tzcnt donne le couloir le plus bas : ordre croissant conservé.
        while (m != 0)
        {
            const uint32_t lane = _tzcnt_u32(m);
            hits.push_back(uint32_t(i) + lane);
            m &= m - 1;                            // éteint le bit traité
        }
    }
}
