0.1 · Pourquoi ce lot

Le moteur savait dessiner deux vues côte à côte. Dès qu’on a voulu en afficher quatre, chaque hypothèse « il y a deux caméras » cachée dans le code est devenue un défaut visible : un tableau trop court, un plafond écrit en dur à trois endroits, un réglage de lisibilité partagé entre des caméras qui n’ont rien en commun. Ce lot remplace ces hypothèses par des règles écrites.

Tout est parti d’une question d’Onky : pourquoi limiter le nombre de caméras dans engine.json alors qu’on peut en ajouter autant qu’on veut dans la scène ? La réponse a fait apparaître que deux nombres différents portaient le même nom : le nombre de caméras que la scène contient, et le nombre de viewports que l’écran affiche.

0.3 · Contexte et objectif fonctionnel

Ce qu’est un viewport, côté éditeur de jeu

Dans Unity ou Unreal, une fenêtre de scène montre le jeu vu par la caméra de gameplay, et des vues d’édition (dessus, côté, perspective) le montrent sous d’autres angles. Le nombre de vues affichées est un choix de présentation. Le nombre de caméras dans la scène est un fait de contenu. Si on les confond, ajouter une caméra de debug dans le JSON change la mise en page, et désactiver une caméra arrête le programme.

Les objectifs du lot

  1. Choisir le nombre de vues indépendamment du nombre de caméras (viewport.maxViewport), et pouvoir changer de caméra quand il y en a plus que de vues.
  2. Garder la vue de jeu : le slot 0 montre toujours une caméra de catégorie Gameplay ; sans caméra de jeu active, le programme s’arrête avec un message.
  3. Ne jamais afficher deux fois la même caméra de debug, et dégrader proprement (avertissement une seule fois) quand il manque des caméras.
  4. Chaque caméra a sa propre plage de lisibilité Depth, avec un défaut global dans engine.json (bug 66).
  5. Poser une caméra sur un axe sans deviner : la rotation se dérive de Forward().
  6. Les gizmos : un asset manquant n’éteint pas toute la scène (55) et la teinte grise reste observable (56).

1 · Laboratoires — voir les règles avant le code

Les laboratoires sont des modèles : ils appliquent les règles écrites dans le carnet et A11, avec les mêmes noms, mais ne sont pas le code du moteur. Les calculs sont en float32 (Math.fround) comme le CPU. L’ordre de tri des priorités (croissant ici) est un choix du modèle : les règles testées n’en dépendent pas.

1.1 · Les slots : combien de vues, quelle caméra dans chacune

Règle (A11) : nombre désiré = min(maxViewport, kMaxCamerasHard) ; possible = 1 slot de jeu + une vue par caméra debug active ; la mise en page n’existe qu’à 1, 2 ou 4 vues, donc on arrondit vers le bas. Aucune caméra de jeu active : arrêt. Les boutons F2 à F8 avancent la caméra du slot à la suivante, en sautant celles déjà affichées dans un autre slot.

slot 0 — Gameplay slots 1.. — Debug

Journal de l’attribution

Ce qu’il faut essayer. (1) Réglage par défaut : 4 vues, jeu = FPS, debug = Overview, Left, Bottom. F4 donne Right, pas Left ni Bottom, qui sont déjà affichées : c’est IsCameraUsedByOtherDebugSlot. (2) Caméras Debug = 2 : trois vues possibles, la mise en page n’en a pas : arrondi à 2 avec un avertissement. (3) Caméras Gameplay = 0 : arrêt. (4) Cocher le contre-exemple, caméras Debug = 2, maxViewport = 2 : l’ancien code compte 4 caméras, veut 4 vues, et s’arrête parce que le plafond est 2.

1.2 · Poser une caméra sur un axe

Une caméra est placée à 120 unités de l’origine et doit la regarder. Le laboratoire calcule Forward et Up avec la composition q_yaw · q_pitch · q_roll (float32), puis le produit scalaire de Forward avec la direction caméra → origine : 1 signifie « l’origine est pile au centre de l’image », −1 « la caméra tourne le dos ».

1.3 · La plage de lisibilité Depth : une constante pour tous, ou une par vue

Le mode Depth affiche t = Saturate(dist / depthDisplayRange), puis un gamma 1/2,2. Au-delà de la plage, t vaut 1 et tous les pixels sont blancs : l’image ne contient plus d’information. Une constante unique de 80 (le défaut d’engine.json) ne convient pas à une caméra dont la scène est à 120 unités.

Huit pixels dans un registre AVX2 (une voie par pixel)

2 · La technique, expliquée

2.1 · Deux nombres, deux plafonds

Le moteur a besoin de deux bornes qui ne s’appliquent pas au même moment. kMaxCamerasHard (constexpr, 4) dimensionne les tableaux : Panel panels[...], bindings, views, renderedCameras, et le tampon de BuildCameraBindings. Un tableau dont la taille se connaît à la compilation ne coûte aucune allocation par frame. viewport.maxViewport est le choix de l’utilisateur ; il est lu et borné par std::min une seule fois, à LoadFromJson. Aucun site d’usage ne répète le min : un plafond répété est un plafond qu’on oublie.

2.2 · Pourquoi 1, 2 ou 4 et jamais 3

BuildLayout produit cinq dispositions (Single, SplitH, SplitV, Quad, MainSide) : 1, 2 ou 4 rectangles. Il n’existe pas de disposition à trois vues. SnapToSupportedViewportCount ramène donc toute demande à la valeur supportée inférieure (3 → 2). C’est un contournement assumé, pas une absence de décision : le troisième layout est reporté (roadmap PH1E-3).

2.3 · Le contrat de BuildCameraBindings

La fonction reçoit slotCount et le nombre de caméras n à placer. Le contrat tranché est n == slotCount : un n plus petit voudrait dire qu’une vue demandée n’a pas de caméra, silencieusement. La fonction tourne à chaque frame ; en cas de violation elle fait Logger::warn et return 0, jamais un assert seul, qui n’existe pas en Release (patron PH1C.b). L’off-by-one corrigé : n >= LV3_MAX_VIEWPORT rejetait Quad qui remplit exactement les 4 cases ; la garde correcte est n > kMaxCamerasHard.

2.4 · Attribution des slots, chaque frame

Le slot 0 reçoit une caméra Gameplay active ; seule panels[0].camera est touchée par F2 (une première version balayait toutes les caméras de jeu et faisait osciller FPS et Follow). Les slots 1 à slotCount − 1 reçoivent des caméras Debug actives, triées par priorité. IsCameraUsedByOtherDebugSlot interdit qu’une même caméra occupe deux slots ; un assert en _DEBUG dans BuildCameraBindings garde le même invariant. Si une caméra devient inactive en cours d’exécution, son slot en prend une autre au prochain recalcul. Le message de dégradation n’est émis que sur le changement d’état (front), pas à chaque frame.

2.5 · Donnée de session, donnée d’auteur

Ce qui vit dans le JSON (depthDisplayRange, far, priority) est une donnée d’auteur : elle suit CameraComponent → ViewData dans BuildViewData. Ce que l’utilisateur change en jouant (le mode de rendu d’un slot, la caméra choisie) est une donnée de session : elle suit Panel → CameraBinding → ViewData. Le bug 66 se corrigeait dans le premier trajet ; l’écrire dans le second aurait fonctionné et mélangé deux responsabilités. Même idée pour R20 : depthDisplayRange est un choix de lisibilité, jamais dérivé de farPlane, parce que partager l’unité (des unités monde) ne fait pas de deux grandeurs la même grandeur.

2.6 · Gizmos : ne pas éteindre toute la scène pour un asset

Le bug 55 était une garde en || suivie d’un corps qui supposait &&. Le correctif garde chaque bloc par le booléen qui l’a rempli. GizmoAssets::IsValid() vaut « au moins un des deux » ; SpawnCameraGizmos saute une caméra dont l’asset de sa projection manque (avertissement nommé), pas toute la scène ; Test_GizmoCountMatchesCameras(Registry&, const GizmoAssets&) compte pareil. Pour le 56, m_visible a été retiré du composant : un champ écrit et jamais lu par un filtre actif ment sur le comportement.

2.7 · Rotation : la formule, pas l’œil

Un angle d’Euler en degrés (JSON) devient Quatf(eulerDeg, true) avec x = pitch, y = yaw, z = roll, composé en q_yaw · q_pitch · q_roll. On applique ce quaternion à Forward() = (0, 0, −1) et on exige que le résultat pointe vers l’origine. Pour le pitch : une rotation θ autour de X envoie (0, 0, −1) sur (0, sin θ, −cos θ). L’annexe A11 écrit −sin θ ; c’est une erreur de signe de la formule (amendement AM2), sans effet sur les valeurs livrées qui, elles, sont justes (Top = −90°).

AM2 · Annexe A11 §6.3 et architecture-rules.md : signe de la formule du pitch
Avant
Rotate_X(Forward, θ) = (0, -sinθ, -cosθ)
Top : (y,z) = (-1,0) → pitch = -90°       // la conclusion
                                          // contredit la formule
Après
Rotate_X(Forward, θ) = (0, +sinθ, -cosθ)
Top : (y,z) = (-1,0) → sinθ = -1 → pitch = -90°
Rotate_Y(Forward, θ) = (-sinθ, 0, -cosθ)   // inchangée

Contrôle : avec −sinθ, pitch −90° donnerait (0, +1, 0), une caméra qui regarde en haut ; or Top_View à −90° fonctionne. La rotation droite d’angle θ autour de X envoie (0, 0, −1) sur (0, sinθ, −cosθ). Les valeurs livrées (−90, +90, +90, −90) sont justes ; seule la formule écrite est à corriger. Calcul fait hors moteur avec la composition standard : à confirmer contre Quat::rotate du dépôt avant de modifier A11 (PH1E-6).
