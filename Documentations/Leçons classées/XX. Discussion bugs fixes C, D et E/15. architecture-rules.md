## Architecture rules

- [stated] R11bis (dirty flag contract): only the writer of `m_local` may raise the dirty flag; only `LocalTransformSystem`, after actual recomposition, may lower it — never inside read-only or display systems.
- [stated] S3 (Anchor/Body pattern): orbital position and body orientation never share a node.
- [stated] S4: a component contains only what its system reads/writes.
- [stated] S7, S9: trigger radius is a gameplay value in world units, never inherits scale.
- [stated] S10 (doctrine du temps): time scale is multiplicative, like camera zoom. Two deltas coexist and are never interchangeable: `realDt` (wall-clock, clamped, feeds `SimulationClock::Advance`) drives player/device-facing systems — `PlayerInputSystem`, `CameraFPSControllerSystem`, `CameraFollowSystem` — which must keep responding while the simulation is paused or time-scaled; `simDt` (returned by `Advance`, gated by pause/scale) drives world-simulated systems — `AnimationSystem` (orbites, spins). A system takes whichever dt matches what it represents, jamais les deux, jamais par supposition.
- [stated] S13 (ordre canonique de la boucle principale, discussion D — numéro provisoire à confirmer avec Onky): DEUX passes de cuisson des matrices par frame, pas une. Par frame, dans cet ordre strict — (1) mesurer `realDt`, clamper ; (2) avancer l'horloge (`simDt = _clock.Advance(realDt)`) ; (3) construire l'`InputState` de la frame, toujours avant tout système qui le lit (bug 45 : `PlayerInputSystem` s'exécutait avant `BuildInputState()`) ; (4) systèmes qui écrivent `m_local` d'entités du MONDE — `PlayerInputSystem` sur `realDt`, `AnimationSystem` sur `simDt` ; (5) CUISSON N°1, complète, sur toute la scène — `LocalTransformSystem(registry)` puis `WorldTransformSystem(registry)` : sans cette passe intermédiaire, les systèmes caméra liraient un `m_worldMatrix` vieux d'une frame (`CameraFollowSystem` lisant la position de sa cible juste déplacée par `PlayerInputSystem`) ; (6) systèmes caméra qui LISENT ces matrices fraîches et ÉCRIVENT `m_local` des caméras — `CameraFPSControllerSystem`/`CameraFollowSystem` sur `realDt`, `CameraZoomSystem`, puis sélection de caméra, `BuildCameraBindings`, `CameraGizmoSystem` ; (7) CUISSON N°2, CIBLÉE — `LocalTransformSystem(registry)` (dirty-only, quasi gratuit) puis `WorldTransformSystem(registry, roots)` avec `roots` = les seules caméras rendues cette frame (jamais la forme complète ici : coûterait O(N) pour ~2 entités changées, cf. le pattern de re-cuisson ciblée plus bas) ; (8) `TriggerSystem` et tout ce qui lit `m_worldMatrix` ; (9) construction des vues puis rendu.
- [stated] S11: orbital angles are calculated from the simulated date, never accumulated.
- [stated] S12: an event names a transition, not its context.
- [stated] S1: a scene stores only real physical units.
- [stated] `TriggerSystem` rule (L06): never execute user code inside collision detection; use a flat event queue with Enter/Stay/Exit and no callbacks during iteration.
- [stated] `CameraBinding` separates static associations from derived matrices, avoiding one-frame-lag bugs.
- [stated] A `hasFarPlane` boolean plus an unconditionally assigned `farPlane` is preferred over sentinel values.
- [stated] An `LV3_ASSERT` must always follow, never precede, the assignment it verifies (bug 60, `BuildViewData`, `System.cpp`): `LV3_ASSERT(cam.m_infiniteFar || std::isfinite(v.farPlane))` placed before `v.farPlane = cam.m_farPlane;` silently tested `ViewData::farPlane`'s default member initializer (`= 1000.0f`, always finite) instead of the value about to be written — a guard that could never fire, not undefined behavior. Same discipline already used for `aspect` two lines above in the same function: compute, then assert immediately on the value just computed, never on a stand-in that happens to share the field's name.
- [stated] Bug 61 (Discussion E, evolved in Discussion J) — two-tier viewport cap, never a per-frame `std::vector`: `kMaxCamerasHard` (`Core/EngineSettings.h`, `constexpr size_t`, equals `LV3_MAX_VIEWPORT`) is the compile-time hard ceiling that sizes every stack buffer touching camera bindings (`BuildCameraBindings`'s local `vps[]`, `main.cpp`'s `Panel panels[]`/`views[]`/`g_cycleCam[]`/`g_cycleMode[]`) — it never moves at runtime. `EngineConfig::ViewportConfig::maxViewport` (`engine.json`, key `viewport.maxViewport` — **renamed from `camera.maxCameras` in Discussion J**: it caps desired *viewports*, not *cameras*, and the old name claimed otherwise) is the runtime-tunable soft cap, clamped against `kMaxCamerasHard` via `std::min` exactly once, at `LoadFromJson` — never re-clamped ad hoc at each call site. Applies generally: any future per-frame system needing an N-bounded stack buffer should split its cap the same way — a named compile-time `kXxxHard` for the buffer, a config-time value clamped against it once, never a runtime-resizable container in the hot path.
- [stated] `BuildCameraBindings` contract: `slotCount` is not spare buffer capacity — `layout` is chosen by the caller *from* `slotCount` (one viewport per requested camera), so `n == slotCount` is the correct precondition, not `n <= slotCount`. A violation is a caller bug (never user input), so it is handled with `Logger::warn` + `return 0` rather than `LV3_ASSERT`, specifically because this function runs every frame and an assert here would kill the program on every tick until fixed, whereas the caller (`main.cpp`) already turns a `0` return into a clean, single, loud loop shutdown.
- [stated] `BuildLayout` (`CameraBinding.CPP`) constraint, load-bearing: only produces 1, 2, or 4 viewports (`ELayout::Single/SplitH/SplitV/MainSide/Quad`) — no 3-viewport layout exists. Any policy computing a desired viewport count must snap 3 down to 2 (never up to 4 — a fourth slot would show a camera nobody asked for), with a degraded-mode warning. Adding `ELayout::Triple` is explicitly deferred (Onky, twice) — see Carnet de route, "Prochaines actions".
- [stated] Viewport/camera decoupling (Discussion J, bug 61 extension — Annexe A11): the number of displayed viewports is decoupled from the number of active cameras in the scene. Exactly one slot (index 0) is always reserved for the `Gameplay` category (cycled among active gameplay cameras if more than one); the remaining `maxViewport - 1` slots are `Debug`-category, cycled independently with collision avoidance (`IsCameraUsedByOtherDebugSlot`) so two debug slots never show the same camera at once — `BuildCameraBindings`'s own `_DEBUG`-only assert independently guards the same invariant. Fatal stop (not a degraded mode) if zero active `Gameplay` camera exists. Any total other than {1, 2, 4} is snapped down per the `BuildLayout` constraint above, with a `Logger::warn` edge-triggered on total change (not every frame).
- [stated] Session-chosen data vs. author-owned data — two different pipelines, never merge them: a value the *user* selects at runtime (which camera is showing, which render mode a slot displays) is session state and flows `Panel → CameraBinding → ViewData` (`mode`, `m_camera`). A value the *scene author* sets per camera (`near`, `far`, `fov`, `depthDisplayRange`) is authored data and flows directly `CameraComponent → ViewData` in `BuildViewData`, bypassing `Panel`/`CameraBinding` entirely — it is never something the keyboard cycles. Confusing the two (e.g. routing a debug-readability constant through the session-state path, or making an authored camera property depend on which slot currently shows it) reproduces the R12 bug (bug 66) in a new location.

## Rendering pipeline learnings

- [stated] Reverse-Z (`near → 1`, `far → 0`): the two non-linearities (perspective `1/z` storage + float ULP distribution) cancel rather than compound; depth clear = `0.0f`, early-Z test uses `>`; enables an infinite far plane via `PerspectiveInfinite()`.
- [stated] Orthographic camera immobility on forward/backward motion is a mathematical property (no Z division), not a bug.
- [stated] Front-face area is negative in raster space (Y-flip); the backface culling sign must account for this.
- [stated] Clipping seam cracks require both an antisymmetric `EdgeFunction` formulation and a canonical-order `ClipLess` comparator.
- [stated] `invW` is the critical passenger across the clip→NDC boundary; `nearPlane`/`farPlane` in `FragmentContext` were retired in favor of `invW`-based distance reconstruction.
- [stated] Camera gizmos (Discussion E, bug 56): the validated policy (A5 §4.5) is that every camera's gizmo stays visible every frame — only tint (amber for the active camera, cold gray otherwise) distinguishes it. As of the current source, `DebugVisualComponent::m_visible` has been removed from the struct entirely (commented out), not merely left declared-but-unwritten — the alternative "Unity-style" policy (A9 §11.2, only the active camera's frustum drawn) is a deliberately deferred, explicitly non-adopted debt, not a silently half-wired feature. `RenderView`'s filter reads only `m_hideForCamera`; reviving the A9 §11.2 policy would mean reintroducing a visibility field explicitly, not just starting to write one that was quietly kept around.
- [stated] `GizmoAssets::IsValid()` (question rouverte par Onky après bug 56, tranchée et confirmée testée le 20/09/2026) is `||`, not `&&`: one loaded mesh (perspective or orthographic) is enough for the asset set to be usable — a `GizmoAssets` is legitimately partially valid (already established by bug 55's fix). Per-camera fallback lives in `SpawnCameraGizmos`: `const MeshHandle want = assets.For(cam.m_projection); if (!want.IsValid()) { Logger::warn(...); continue; }` — a camera whose own projection's asset failed to load is skipped individually, with a named warning, never a blanket refusal for the whole scene. `TestAffichageGizmoCamera.cpp::Test_GizmoCountMatchesCameras(Registry&, const GizmoAssets&)` mirrors the same rule on the test side: `expected` counts a camera only if `cam.m_gizmoLength > 0.0f && assets.For(cam.m_projection).IsValid()`, not every camera that merely requested a gizmo.
- [stated] R20 (readability values are not geometric values, `Annexe_A5` §13.3): a debug-display parameter like `depthDisplayRange` is chosen for output legibility, never derived from a geometric quantity like `farPlane` — sharing a unit (world units) does not make two quantities the same quantity.
- [stated] R12 — resolved (Discussion J, bug 66): `Renderer::SetDepthDisplayRange` must be called once **per view**, never once per frame before the view loop — a single call before the loop silently shares one readability constant across every simultaneous camera, saturating the `Depth` mode's output for any camera whose distance profile differs from whichever camera the constant was tuned against. Fix: `CameraComponent::m_depthDisplayRange` (optional per-camera override, sentinel `-1.0f` = unset) is read in `Serializer.cpp`, resolved against the `EngineConfig::debug.depthDisplayRange` global default inside `BuildViewData` (`System.cpp`) into `ViewData::depthDisplayRange`, and applied in `RenderSystem.cpp::RenderView` right after `renderer.SetMode(view.mode)`. Follows the session-data/author-data split above: this is authored-data routing, not session-state routing.
- [stated] Camera rotation convention, confirmed by reading `Vectorlib.h`/`Transform.h`/`QuaternionLib.h`/`Serializer.cpp` (Discussion J): right-handed, Y-up. At identity, `Forward() = (0,0,-1)`, `Right() = (1,0,0)`, `Up() = (0,1,0)`. JSON `"rotation"` is Euler degrees consumed via `Quatf(eulerDeg, true)`, with `Angles.x = Pitch (X)`, `Angles.y = Yaw (Y)`, `Angles.z = Roll (Z)`, composed as `q_yaw * q_pitch * q_roll` (order Y-X-Z). Derived, verified formulas for placing a camera on a cardinal axis without guessing: pure pitch θ on `Forward()` gives `(0, -sinθ, -cosθ)` — top camera (looking down -Y) needs `pitch = -90°`, bottom (looking up +Y) needs `pitch = +90°`. Pure yaw θ on `Forward()` gives `(-sinθ, 0, -cosθ)` — a camera on +X looking toward -X needs `yaw = +90°`, a camera on -X looking toward +X needs `yaw = -90°`. Both cases leave `Up()` non-degenerate (no gimbal lock at these specific angles). Never guess a rotation value by analogy with a sibling camera — derive it from `Forward()` every time (a mis-guessed rotation produced a camera that rendered nothing, mistaken for a switching bug before this derivation caught it). Full derivation: Annexe A11.
- [stated] Chantier 2 (27/09/2026, Avenant C2) — vertex stage: a computation that depends only on the vertex is done once per vertex, never once per face corner. `RenderView` runs `TransformPositions(mvp, vertexPositions, n, clipBuf.Data())` once per (instance, view) — not per (mesh, view): `mvp` includes the entity's model matrix — then faces only READ three `Vec4f` by index. `ClipSpaceBuffer` (`Rendering/VertexStage.h`) is owned by the CALLER (like `fb`/`db`), sized once by `kMaxMeshVerticesHard` (= `LV3_MAX_MESH_VERTICES`, `Core/EngineSettings.h`), never a local or `static` vector. The vertex cap is enforced once in `ResourceManager::RegisterMesh` (single entry gate for every mesh); `RenderView` keeps `LV3_ASSERT` + a Release `continue` guard (bug 53 pattern). `TransformPositions` copies `mvp` into a local to defeat float aliasing with `dst`, and is the single site for the future AVX2 version (chantier 4).
- [stated] Clip-space buffer stays `Vec4f`, never `Vec3f`: object-space w is implicitly 1 (input `Vec3f`), but clip-space w = -z_view varies per vertex and is read by `NearDistance`, `Lerp`, `ClipLess`, `invW`, fragments. Dividing by w before near clipping is forbidden (w < 0 behind the camera flips x/y).

## ECS / systems learnings

- [stated] Entity versioning: 16-bit index / 16-bit generation packing in `Entity` (repack from the original 24/8 split — décidé pour le bug 54 : 65 536 entités max, 65 536 recyclages d'un slot avant bouclage de l'ABA, marge ×16 au-dessus de `LV3_MAX_ENTITIES`).
- [stated] The `ComponentView` iterator must use its captured storage pointer tuple directly, not re-query the Registry per entity.
- [stated] A paged sparse array (`PagedSparseArray`, 4096 entries/page) prevents memory waste with high entity indices.
- [stated] `active`/`priority` (camera lens, render policy) and `enabled` (controller, system writes) are distinct, orthogonal concepts.
- [stated] Targeted re-bake pattern: `WorldTransformSystem(registry, roots)` re-propagates only the given root entities (and their descendants) instead of retraversing the whole scene — reuses `PropagateWorld` directly. Used for the second per-frame bake pass (cameras + their gizmo children), so its cost stays O(rendered cameras) rather than O(N) as the scene grows. Precondition, asserted (`LV3_ASSERT(IsRoot(registry, e))`), never assumed: every entity in `roots` must actually be a root (no parent) — a camera qualifies today because no scene parents a camera.

## Testing

- [stated] TNR (non-regression test) system is based on `JsonReader` with `WarnUnread()`, with numbered bugs tracked in a journal.
- [stated] Coverage tests (pixel-counting) are effective for diagnosing clipping correctness.
- [stated] All new systems integrate with the `WarnUnread`/`LV3_ASSERT`/`Logger` pattern.
- [stated] A vacuity guard on a loop-based test must generalize with the scene, not hardcode an entity count (A9 §8, Discussion E correction): `LV3_ASSERT(n == 2)` broke the instant a third camera existed; the code's actual invariant — `LV3_ASSERT(declared == 0 || nGizChecked > 0)` — says "if anything declared work, at least one unit of it was actually checked", which holds for any scene.

## Measurement rules (series M — Consolidation C2 + Avenant chantier 2)

- [stated] M1 Release only; M2 every CSV header carries its context — scene, config, res, views, overhead, plus `cpu=`, `affinity=`, `ablation=` (each added after a real mistake); M3 two control quantities per campaign — compute T = Animation + LocalXform1 + WorldXform1 + Trigger, and memory `Clear`; a pair is admissible only if T differs by < 3 %; M4 one variable at a time; M5 median/p95/max, never mean or mean FPS; M6 one home for build switches (`LV3.Common.props`) + `[Build]` self-report line.
- [stated] M7 (amended, Avenant chantier 2): an ablation measures a stage in ISOLATION, not its contribution to the frame — never derive a neighbouring stage's cost by subtraction (full − ablation): an out-of-order core overlaps independent work (e.g. next face's `MulRow`) with the rasterizer's memory stalls, even single-threaded. Ablation is a compile switch `LV3_ABLATION_RASTER` declared in the CSV header, never a hand-commented block.
- [stated] M8: two versions are compared in the SAME session, interleaved ABBA after one discarded warm-up run; the verdict is the ratio within each pair, never absolute values from two sessions (±0.4 % within pairs vs ~15 % between sessions).
- [stated] M9: on a hybrid CPU (dev laptop i7-1265U, 2 P-cores + 8 E-cores) a single-threaded bench is pinned (`start /affinity 4` = P-core; `100` = E-core); the reference is taken on P-core. Unpinned runs silently land on E-cores (×1.5 on T, ×1.8 on Render). Reference F (P-core, chantier 2 in): Render 10.19 ms, frame 12.14 ms, T 93.6 µs, Clear 968 µs, ≈ 37 ns per submitted face. C2 absolute figures came from another machine and are not comparable.
