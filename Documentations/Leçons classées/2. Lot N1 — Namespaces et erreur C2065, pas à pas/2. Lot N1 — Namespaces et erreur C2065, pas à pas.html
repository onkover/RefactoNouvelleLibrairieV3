Lot N1 — Les namespaces et l’erreur C2065, pas à pas

LibraryV3 (LIB) · RefactoNouvelleLibrairieV3 (EXE) · Visual Studio 2026 · MSVC

Objectif. Comprendre pourquoi le compilateur ne connaît pas LibV3 dans main.cpp, maîtriser la mécanique des namespaces (existence, recherche de noms, déclaration/définition, imbrication) et corriger sans deviner.
Introduction. Chaque .cpp est compilé seul. Un namespace n’existe, pour ce .cpp, qu’à partir du moment où une ligne namespace LibV3 { … } a été lue — directement ou via un #include. Ce que voit ConfigManager.cpp est invisible pour main.cpp.

2. Leçon — les 6 règles des namespaces

R1 — Un namespace est « ouvert ». On peut le rouvrir dans autant de fichiers qu’on veut : chaque namespace LibV3 { … } ajoute des noms au même ensemble.

R2 — Il n’existe qu’après lecture. Dans une unité de traduction (le .cpp + tous ses #include développés), un nom de namespace est inconnu tant qu’aucune déclaration n’a été lue. Seuls les headers propagent.

R3 — Trois façons d’y accéder, du plus précis au plus large.

LibV3::Logger::error("x");     // qualifié : explicite, jamais ambigu
using LibV3::Logger;           // using-declaration : UN nom
using namespace LibV3;         // using-directive : TOUS les noms (le plus large)

R4 — La using-directive ne va jamais dans un header (elle s’imposerait à tous les .cpp qui l’incluent). Dans un .cpp, après les #include, et seulement si on utilise vraiment le namespace. Idéal : portée de fonction.

R5 — Déclaration et définition désignent la même entité. Trois écritures de définition, une seule piège :

namespace LibV3 { void f() {} }          // OK  -> ?f@LibV3@@YAXXZ
void LibV3::f() {}                        // OK  -> ?f@LibV3@@YAXXZ
using namespace LibV3; void f() {}        // PIÈGE : définit ::f -> ?f@@YAXXZ

R6 — Recherche non qualifiée : de l’intérieur vers l’extérieur, on s’arrête à la première portée qui contient le nom (même si la signature ne convient pas : c’est le masquage, section 7).

Algorithme de la recherche d’un nom n depuis une portée S :
1. Pour chaque portée P de S jusqu’au global (intérieur → extérieur) :
  a. noms propres de P + noms des namespaces importés par un using namespace dont la « portée effective » est P ;
  b. si au moins un trouvé : STOP (si plusieurs entités distinctes : ambiguïté, C2668) ;
2. Si rien : erreur « identificateur non déclaré » (C2065).
Portée effective d’un using namespace N écrit dans S : le plus proche namespace englobant à la fois S et N. Pas de version vectorisée : résolu à la compilation.

6. Pourquoi un namespace dans un namespace ?

Syntaxe : namespace LibV3 { namespace Math { … } }, ou depuis C++17 : namespace LibV3::Math { … }.

① Découper par sous-système. LibV3::Math, ::Render, ::Scene. Le nom dit d’où il vient et évite les collisions (Point de windows.h, clamp…).
② Cacher l’implémentation. LibV3::detail : « ne pas appeler de l’extérieur ». Convention, pas protection du compilateur. Ton json.hpp fait pareil avec nlohmann::detail.
③ Choisir l’implémentation SIMD. Math::scalar (référence) et Math::avx2 (rapide) coexistent ; le moteur n’en expose qu’une. Section 8.
④ Versionner (inline namespace). namespace LibV3::inline v2 { … } : les noms restent utilisables comme LibV3::f, mais le nom décoré contient v2 : une vieille .lib ne se lie pas silencieusement avec un nouveau header. nlohmann utilise un inline namespace versionné.
⑤ Namespace anonyme. namespace { int cache; } : visible dans ce seul .cpp (liaison interne, successeur de static). Jamais dans un header.
⑥ Alias local. namespace fs = std::filesystem; (ce que fait ton ProgrammeConfig) : raccourcit un nom long sans rien importer.
Le prix : chaque niveau ajoute une portée dans la recherche (R6), donc un risque de masquage. Règle pratique : 2 niveaux maximum (LibV3::Math), un nom unique par concept.

8. Les namespaces au service du scalaire / vectorisé (et CE3)

Seul endroit de ce lot où un équivalent vectorisé existe. Même interface, deux implémentations rangées dans deux namespaces imbriqués :

Scalaire
namespace LibV3::Math::scalar {
  inline float dot8(const float* a, const float* b) {
    float s = 0.0f;
    for (int i = 0; i < 8; ++i) s += a[i] * b[i];
    return s;
  }
}
AVX2 (8 couloirs)
namespace LibV3::Math::avx2 {
  inline float dot8(const float* a, const float* b) {
    __m256 p  = _mm256_mul_ps(_mm256_loadu_ps(a),
                              _mm256_loadu_ps(b));
    __m128 s4 = _mm_add_ps(_mm256_castps256_ps128(p),
                           _mm256_extractf128_ps(p, 1));
    __m128 s2 = _mm_add_ps(s4, _mm_movehl_ps(s4, s4));
    __m128 s1 = _mm_add_ss(s2, _mm_shuffle_ps(s2, s2, 1));
    return _mm_cvtss_f32(s1);
  }
}
namespace LibV3::Math {
#if defined(__AVX2__)
    using avx2::dot8;      // Math::dot8 -> version rapide
#else
    using scalar::dot8;    // Math::dot8 -> version de référence
#endif
}   // Math::scalar::dot8 reste toujours appelable : c'est le témoin des tests
CE3 : sur le cas piégeux, un test assert(scalar::dot8(a,b) == avx2::dot8(a,b)) échoue (5 contre 4) alors que la valeur exacte vaut 6. Les deux ordres de sommation sont « corrects » en float32. Le test doit comparer à une référence en double avec une tolérance relative, jamais deux float32 avec ==.
