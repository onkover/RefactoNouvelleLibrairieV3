## 0. État de départ (audit du dossier `Maths/`)

Le dossier contenait **deux familles de types concurrentes**, et `Ressources/MathTypes.h` incluait **les deux** :

| | Famille **héritée** (scratchapixel) — *canonique* | Famille « moderne » (redondante) |
|---|---|---|
| Fichiers | `Vectorlib.h`, `MatrixLib.h`, `QuaternionLib.h` | `Vec2f/3f/4f.h`, `Matrix44f.h/.cpp`, `Quat.h`, `AABB3d`, `Plane`, `Frustum`, `Transform` |
| Forme | templates `Vec3<T>`, `Matrix44<T>` | `struct` float concrètes |
| Namespace | global (aucun) | `LibV3` pour les vecteurs, `LibV2` pour le reste |
| Matrices | **row-major**, vecteur-ligne `v·M`, builders en post-multiplication (**S·R·T**) | colonne-majeur, vecteur-colonne `M·v`, T·R·S |

**Le piège observé :** `Vec3f` désignait **deux types différents** selon le namespace d'écriture. Et un troisième jeu de conventions traînait dans l'ancien `Lecon_02_Mathematiques.md` (main gauche / colonne-majeur / `[0,1]`). **Trois sources, trois conventions.**

> **Principe directeur :** en 3D, une convention non décidée est un bug qui dort. On n'en garde **qu'une seule**, et c'est celle du code.

## 1. Pourquoi une bibliothèque maison plutôt que GLM

En production : on prend GLM, DirectXMath ou Eigen, point. Libs blindées, vectorisées SIMD, éprouvées.

Mais **LibraryV3 est un moteur d'apprentissage CPU**, ce qui inverse la décision :

- **Comprendre, pas consommer** — impossible d'auditer un rasterizer sans maîtriser *exactement* la multiplication matrice-vecteur.
- **GLM a la forme du GPU** — son API mime GLSL. Un *software renderer* CPU veut ses propres ergonomies (contrôle du NDC, de la profondeur, du balayage).
- **Contrôle total du layout mémoire** — indispensable pour le SIMD et le rendu par tuiles (`LV3_TILE_SIZE`) : alignement, AoS vs SoA.
- **Zéro dépendance, débogabilité totale** — point d'arrêt possible dans chaque opération.

> ⚠️ **Piège :** « maison ≠ plus rapide ». Au début, la lib est *plus lente* que GLM. La valeur est **pédagogique et architecturale**.

## 3. Les décisions dictatoriales (D10–D18)

La numérotation poursuit celle de L01. Source de vérité : l'artefact « Lot L02 pas à pas ».

| # | Décision | Statut |
|---|---|---|
| **D10** | Une seule famille canonique : la **famille templatée** (`Vectorlib`, `MatrixLib`, `QuaternionLib`). Les fichiers modernes redondants sortent du build. | ✅ tranchée |
| **D11** | **Namespace unique `LV3`** (même racine que le préfixe `LV3_`). | ✅ tranchée |
| **D12** | **Row-major `m[row][col]`**, **vecteur-ligne `v' = v·M`**, composition **S·R·T** lue de gauche à droite, translation en **ligne 3**, **monde = local · parent**. | ✅ tranchée |
| **D13** | **Repère main droite**, Y en haut, **la vue regarde vers −Z**. Vérifié : `rotateX(+90°)` envoie +Y vers +Z, `crossProduct` donne X × Y = +Z. | ✅ tranchée |
| **D14** | Profondeur NDC **`[0,1]` reverse-Z** (near → 1, far → 0). *(La proposition `[-1,1]` de l'échange est caduque — décidée en L05.)* | ✅ tranchée (L05) |
| **D15** | **Tout en 4×4.** Point → `multVecMatrix` (w = 1, translation, division par w). Direction → `multDirMatrix` (w = 0, bloc 3×3). Normales → `inverse().transposed()` puis `multDirMatrix`. **Pas de type `Mat3`.** | ✅ acceptée |
| **D16** | Les fabriques de matrices (vue, projection) sont des **fonctions pures** hors de `Camera` (fichier `Projection.h`, pas méthodes de `Matrix44`). | ✅ acceptée, affinée L05 |
| **D17** | Noms hérités conservés : `dotProduct`, `crossProduct`, `norm`, `Normalized`. *(⚠ `norm()` = longueur AU CARRÉ : piège, dette L2-14.)* | 🔵 proposée |
| **D18** | Les `operator[]` prennent un **`int`** (évite la conversion restrictive C4244). | ✅ appliquée |

### Convention officielle du moteur LV3 (verrou)

```
Repère     → main droite, Y haut, vue vers −Z
Rangement  → row-major, m[row][col]
Multiplic. → vecteur-ligne, v' = v·M
Compo      → S·R·T (gauche → droite) ; monde = local · parent
Profondeur → NDC [0,1] reverse-Z (near→1, far→0, test GREATER, clear 0)
Namespace  → LV3 unique
Précision  → float partout (double réservé aux accumulations rares)
```

## 4. Conséquences du verrou (à retenir pour tous les lots suivants)

1. **Composition** : `monde = local · parent` (la locale à gauche touche le vecteur en premier). Jamais l'inverse.
2. **`LookAt` / `Perspective`** : les formules des livres **OpenGL se recopient transposées**. Piège n°1 quand on s'inspire d'un tutoriel.
3. **Projection perspective** : la matrice **part de zéro**, pas de l'identité (sinon `m[3][3] = 1` casse la division par w). Colonne 3 = `(0, 0, −1, 0)`, donc **`w = −z`** = distance devant la caméra (main droite).
4. **Normales** : `model.inverse().transposed()` puis `multDirMatrix`. Sous scale non uniforme, passer par la matrice monde brute fait **pencher les normales** → éclairage faux (contre-exemple C3).
5. **Reverse-Z** : la zone fine du flottant (près de 0) tombe au *far*, là où la projection en 1/z écrase le plus — les deux non-linéarités se compensent. Impossible en `[-1,1]`.

---

## 5. Sujets ajoutés au programme

1. **Transform S·R·T** — position + rotation quaternion + scale, matrices locale et monde en cache.
2. **Gimbal lock et quaternions** — *pourquoi* stocker les rotations en quaternion plutôt qu'en angles d'Euler.
3. **Transformation des normales** — `inverse().transposed()` + bloc 3×3 (D15).
4. **Robustesse numérique** — jamais de `==` sur des flottants ; garde anti division-par-zéro dans `Normalized` ; distinction `EPSILON_FLOAT` (tolérance) vs `NEAR_ZERO` (garde) héritée de L01.
5. **Alignement SIMD** — ⚠ *révision* : la vectorisation réelle du moteur (`ProjectPositions8` AVX2) travaille en **SoA** (une composante de 8 sommets par registre), pas en `alignas(16)` sur un `Vec4` isolé. L'alignement qui compte est celui des **tableaux SoA** (`LV3_ALIGN_SIMD`). Dette L2-9 à décider.
6. **Taxonomie des espaces** — Local → Monde → Vue → Clip → NDC → Écran.
7. **Ne pas optimiser trop tôt** — le mythe du *fast inverse square root* : inutile aujourd'hui.

## 6. Code de référence (forme réelle du dépôt)

Famille templatée, row-major, main droite. Noms hérités conservés (D17).

```cpp
// --- Vec3<T> : produits et longueur ---
template <typename T>
struct Vec3
{
    T x{}, y{}, z{};

    T operator[](int i) const noexcept { return (&x)[i]; }   // index int (D18)

    // Produit scalaire : ((x*vx + y*vy) + z*vz)
    T dotProduct(const Vec3& v) const noexcept
    { return x * v.x + y * v.y + z * v.z; }

    // Produit vectoriel MAIN DROITE : X × Y = +Z (D13)
    Vec3 crossProduct(const Vec3& v) const noexcept
    {
        return { y * v.z - z * v.y,
                 z * v.x - x * v.z,
                 x * v.y - y * v.x };
    }

    // ⚠ norm() = longueur AU CARRÉ (nom hérité, piège — dette L2-14)
    T norm() const noexcept { return dotProduct(*this); }

    Vec3 Normalized() const noexcept
    {
        const T n = norm();
        if (n <= T(0)) return {};                 // garde : pas de division par ~0
        const T f = T(1) / std::sqrt(n);
        return { x * f, y * f, z * f };
    }
};
```

```cpp
// --- Matrix44<T> ROW-MAJOR : m[row][col] ---
template <typename T>
struct Matrix44
{
    T m[4][4];   // row-major

    // Produit : c[i][j] = Σ_k a[i][k] · b[k][j]
    Matrix44 operator*(const Matrix44& b) const noexcept;

    // Point (w = 1) : x' = x*m[0][0] + y*m[1][0] + z*m[2][0] + m[3][0] ...
    //                 translation lue en LIGNE 3, division par w
    Vec3<T> multVecMatrix(const Vec3<T>& p) const noexcept;

    // Direction (w = 0) : bloc 3×3 seul, la ligne 3 est ignorée
    Vec3<T> multDirMatrix(const Vec3<T>& d) const noexcept;

    // Builders en POST-multiplication → S·R·T
    Matrix44& translate(const Vec3<T>& t) noexcept;  // écrit m[3][0..2]
    Matrix44& scale(const Vec3<T>& s)     noexcept;  // diagonale
    Matrix44& rotateZ(T rad) noexcept;               // m[0][1]=+s, m[1][0]=-s
};
```

> **Lecture mémoire :** en row-major, une **ligne** est contiguë. Un registre SIMD charge une ligne d'un coup ; on diffuse `x` dans quatre couloirs et on multiplie. **Aucune transposition, aucune addition horizontale** — c'est l'intérêt direct du row-major pour le CPU.

## 7. Architecture des fichiers `Maths/`

```
Maths/
  MathTypes.h      ← umbrella : inclut Vectorlib.h, MatrixLib.h, QuaternionLib.h
  MathUtils.h      ← Saturate, Lerp (+ ApproxEqual à ajouter — dette L2-11)
  Vectorlib.h      ← Vec2<T>, Vec3<T>, Vec4<T>   (templatés, row-friendly)
  MatrixLib.h      ← Matrix44<T>  (row-major, S·R·T)
  QuaternionLib.h  ← Quat         (Slerp, LookRotation, ToMatrix44)
  Transform.*      ← composite S·R·T
  Geometry/        ← (vide) AABB, Plane, Frustum → leçon dédiée
```

**PCH ou pas ?** Pendant le développement de la lib → **hors PCH** (on édite ces fichiers en permanence). Une fois stabilisés → candidats au PCH. *(Dette L2-10 : `MathTypes.h` tire `<iostream>` via les `operator<<` ; à déplacer dans un header de debug.)*

## 9. Résumé décisionnel

```
REPÈRE      → main droite, Y haut, vue vers −Z
MATRICES    → row-major m[row][col] ; vecteur-ligne v' = v·M ; S·R·T ; monde = local·parent
PROFONDEUR  → NDC [0,1] reverse-Z (near→1, far→0, GREATER, clear 0)
TYPES       → tout en 4×4 ; pas de Mat3 ; normales = inverse().transposed() + multDirMatrix
PROJECTION  → part d'une matrice NULLE ; colonne 3 = (0,0,−1,0) ; w = −z
NAMESPACE   → LV3 unique (fin de LibV2 / LibV3)
PRÉCISION   → float partout

SIMD        → SoA pour les tableaux (pas alignas(16) sur Vec4 isolé) — dette L2-9
RÈGLE D'OR  → la fiche suit le code, jamais l'inverse
```
