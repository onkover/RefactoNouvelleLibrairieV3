Face arrière en espace objet

Avant B5, un lot de 8 faces arrière coûte autant qu'un lot visible : 24 sommets rassemblés, deux aires, deux boîtes, pour tout jeter. B5 répond « sûrement arrière » avec 4 lectures contiguës, sans toucher aux sommets. Tout est calculé ici en float32 (Math.fround après chaque opération), sur une sphère UV de 3 968 faces, caméra et viewport de V1 (1536 × 900).

Avant le code · le schéma

Une face, son plan, et l'œil du bon côté

  1. Une face est un morceau de plan. Son plan coupe l'espace en deux moitiés : la moitié vers laquelle pointe la normale n, et l'autre.
  2. La face est vue si et seulement si l'œil est dans la moitié de la normale. La distance signée de l'œil au plan le dit : n·œil + d > 0.
  3. Ce test ne dépend d'aucun repère. Dans le repère de l'objet, les plans ne bougent jamais : on les cuit une fois. Il suffit d'y amener l'œil.
  4. Deux chemins pour amener l'œil (flèches entre les deux figures) : inverser la matrice du mesh (Scratchapixel), ou lire E dans la mvp (B5). Même point en perspective. E sait en plus être à l'infini (ortho) et porte le signe du miroir.

La méthode en détail · d'où sort E

Six idées, et à quoi sert chaque calcul

1 · Le sens d'un triangle à l'écran ne dépend que du côté de son plan où se trouve l'œil

À quoi ça sert : c'est toute la question du backface culling, réduite à une seule grandeur. Une face vue de devant tourne dans un sens (1 → 2 → 3, comme une horloge vue de face) ; vue de derrière, dans l'autre (l'horloge vue à travers le cadran). Entre les deux, l'œil est dans le plan : la face est vue par la tranche, son aire à l'écran est nulle. Le test « avant / arrière » revient donc à demander de quel côté du plan de la face est l'œil, c'est-à-dire le signe de la distance signée n·œil + d. Il ne reste qu'un problème : connaître l'œil dans le repère de l'objet, où les plans sont cuits.

2 · Une coordonnée clip est un produit scalaire, et « = 0 » est un plan

À quoi sert le produit scalaire : à mesurer un point le long d'une direction. MulRow calcule x_clip = x·m[0][0] + y·m[1][0] + z·m[2][0] + 1·m[3][0] : c'est le produit scalaire du point homogène P = (x, y, z, 1) avec la colonne 0 de la mvp, que j'appelle c0. De même y_clip = P·c1, z_clip = P·c2, w_clip = P·c3. Une colonne de la mvp est donc une « règle » qui mesure une coordonnée clip.

L'ensemble des points où cette mesure vaut 0 est un plan. x_clip = 0 : les points qui tombent sur la ligne verticale centrale de l'écran. w_clip = 0 : les points à profondeur nulle, ceux du plan qui passe par l'œil, parallèle à l'écran. Et comme la mvp part du repère objet, c0, c1, c3 décrivent ces plans directement dans le repère objet, sans aucune inverse.

3 · L'œil est le seul point qui annule x_clip, y_clip et w_clip : d'où E·c0 = E·c1 = E·c3 = 0

Pourquoi ces trois équations : tous les rayons de la caméra passent par l'œil. Le long d'un rayon, x_clip et w_clip grandissent ensemble (même rapport, même pixel). Le seul point commun à tous les rayons ne peut avoir aucun pixel : il faut que x_clip, y_clip et w_clip y soient nuls tous les trois. Vérification en repère vue : l'œil est (0, 0, 0), donc x_clip = f·0 = 0, y_clip = 0, w_clip = −z = 0.

Chaque équation est un plan (idée 2). Les trois plans x_clip = 0, y_clip = 0 et w_clip = 0 passent tous par l'œil, et seulement l'œil leur est commun. Résoudre E·c0 = 0, E·c1 = 0, E·c3 = 0, c'est trouver le point d'intersection de trois plans.

4 · Pourquoi pas c2 (la colonne z)

z_clip ne sert qu'à la profondeur (le Z-buffer). Le pixel (x/w, y/w), et donc le sens de rotation d'un triangle à l'écran, ne lisent jamais z. Et surtout, l'œil n'annule pas z_clip : en reverse-Z, z_clip = near à l'œil (m[3][2] = near dans PerspectiveInfinite). Ajouter E·c2 = 0 donnerait 4 équations pour 4 inconnues, dont la seule solution est E = 0, qui ne veut rien dire. Les colonnes 0, 1 et 3 sont exactement celles que lit la projection à l'écran.

5 · Résoudre : à quoi servent le produit vectoriel et le produit mixte

En 3D, le produit vectoriel b × c fabrique un vecteur perpendiculaire à b et à c (sa longueur est l'aire du parallélogramme b, c). Il résout donc d'un coup « v·b = 0 et v·c = 0 ». Le produit mixte a·(b × c) est le déterminant det(a, b, c) : le volume signé du parallélépipède. Si a est dans le plan de b et c (par exemple a = b), le volume est plat : det = 0.

En 4D (les points homogènes ont 4 coordonnées), il faut un vecteur perpendiculaire à trois vecteurs c0, c1, c3. La recette généralise le produit vectoriel. Empilez les trois colonnes dans une matrice C de 4 lignes × 3 colonnes. La composante k de E est le déterminant 3 × 3 de C privée de sa ligne k, avec le signe (−1)k : c'est un cofacteur. Les lignes de C sont les r_i = (m[i][0], m[i][1], m[i][3]) du code. Chaque déterminant 3 × 3 se calcule par un produit mixte. Par exemple, E.x = det(r1, r2, r3) = r1·(r2 × r3).

Pourquoi E est bien perpendiculaire aux trois colonnes : par construction des cofacteurs, E·v = det[v | c0 | c1 | c3] pour tout vecteur v (développement de Laplace selon la 1re colonne). Pour v = c0, la matrice a deux colonnes égales : déterminant nul, donc E·c0 = 0. Idem pour c1 et c3. Rien à résoudre : la formule donne directement la solution.

6 · Un exemple à la main

Caméra de V1 à l'origine, objet poussé de 5 unités devant elle (model = translation (0, 0, −5)). Dans le repère objet, l'œil doit être en (0, 0, +5).

7 · Orthographique et miroir, sans une ligne de plus

Ortho : w_clip = 1 pour tous les points (c3 = (0, 0, 0, 1)). Aucun point réel n'a w_clip = 0 : l'œil n'est nulle part à distance finie. La formule donne alors E.w = 0. En coordonnées homogènes, (x, y, z, 0) est un point à l'infini dans la direction (x, y, z) : la direction commune de tous les rayons parallèles. Le test s = n·E.xyz devient « la normale regarde-t-elle vers la caméra ? », le bon test en ortho, sans branche.

Miroir : les trois équations fixent E à un facteur près, λ. La formule des cofacteurs choisit un λ précis, dont le signe suit le déterminant de la mvp, donc celui de det(model). Avec une échelle négative, λ < 0 et s change de signe. C'est exactement ce que fait l'aire à l'écran, puisque le miroir inverse le sens de rotation de tous les triangles. Le schéma d'introduction (bouton Miroir) le montre arête par arête.

Et donc : s = L·E

En perspective, E = λ·(œil_objet, 1), donc s = n·E.xyz + d·E.w = λ·(n·œil + d) : c'est la distance signée de l'idée 1, au facteur λ près. L'étape 2b (plus bas) montre sur un vrai triangle que ce n'est pas seulement « du même signe » : l'aire à l'écran vaut exactement −K·(L·E)/(w0·w1·w2).

L'algorithme · B5 face à Scratchapixel

Deux algorithmes, stade par stade

Le problème commun : à chaque frame, pour chaque (instance, vue) et chaque triangle, décider sans projeter ses sommets si la face est arrière. Les deux méthodes reposent sur la même idée géométrique : une face est vue si et seulement si l'œil est du côté de sa normale, signe de n·œil + d. Elles diffèrent sur trois points : comment l'œil est amené dans le repère de l'objet, ce qui arrive aux cas particuliers, et qui a le dernier mot.

Stade 0 · Au chargement, une fois par mesh (identique pour les deux)

pour chaque triangle f = (p0, p1, p2) du mesh :           // en double
    n_brut = (p1 − p0) × (p2 − p0)          // produit vectoriel : perpendiculaire au triangle,
                                            //   orientée par l'ordre 0 → 1 → 2 des indices
    si |n_brut| == 0 : plan[f] = (0, 0, 0, 0) ; continuer   // triangle dégénéré
    n = n_brut / |n_brut|                   // normale unitaire
    d = −n · p0                             // pour tout point P : n·P + d = distance signée au plan
    plan[f] = (n.x, n.y, n.z, d)            // rangé en SoA : nx[], ny[], nz[], d[]
maxAbsD = max |d|                           // B5 seulement : sert au seuil τ

Pourquoi l'espace objet. Les plans des faces n'y bougent jamais : on paie leur calcul une seule fois au chargement, au lieu de transformer des normales à chaque frame. Cela évite aussi un piège classique : en espace monde, une échelle non uniforme oblige à transformer les normales par l'inverse-transposée. Les deux méthodes profitent de cet avantage, elles ne se distinguent qu'à partir du stade 1.

Stade 1 · Une fois par (instance, vue) : amener l'œil dans l'objet

SCRATCHAPIXEL
// 1a. Caméra dans le MONDE
//     (inverse rigide : bon marché)
C_monde = ligne 3 de inverse(view)

// 1b. Ramener ce point dans l'OBJET
//     (inverse GÉNÉRALE à cause de l'échelle :
//      Gauss-Jordan ou affine 3×3)
invModel = inverse(model)
C_obj    = C_monde · invModel   // un POINT, w = 1

Juste et lisible, mais deux hypothèses restent cachées : la caméra a une position finie (faux en ortho), et le rasterizer juge comme la géométrie (faux en miroir, voir le stade 3).

B5
// 1. Lire l'œil dans la mvp (déjà calculée)
//    r_i = (m[i][0], m[i][1], m[i][3])
E.x =  r1 · (r2 × r3)    // un déterminant 3×3
E.y = −r0 · (r2 × r3)    //   par composante,
E.z =  r0 · (r1 × r3)    //   par produit mixte
E.w = −r0 · (r1 × r2)
// seul point envoyé sur x = y = w = 0 :
//   perspective : E = λ·(œil_objet, 1)
//   ortho       : E = λ·(direction, 0)
//   miroir      : λ < 0

// 2. Seuil de prudence (voir stade 3)
τ = (1/64)·( |E.xyz| + |E.w|·maxAbsD )

Aucune inverse : la mvp sert déjà à projeter les sommets. Aucune division : on ne calcule jamais E.xyz / E.w, donc rien ne déborde quand l'œil part à l'infini. Une seule source de vérité : si la projection change (décentrée, filmback, ortho, future caméra), E suit sans retouche. Environ 40 opérations, plus une racine pour τ.

Stade 2 · Pour chaque face : la distance signée

SCRATCHAPIXEL
s = n · (C_obj − p0)      // = n·C_obj + d
B5
s = ((nx·E.x + ny·E.y) + nz·E.z) + d·E.w
// perspective : s = λ·(n·œil + d)
// ortho       : s = λ·(n·direction)
// ordre FIGÉ, sans FMA : le filet Debug
//   compare SIMD et scalaire au bit près

Formules jumelles : quatre produits, trois additions. B5 garde simplement la 4e composante E.w au lieu de l'avoir figée à 1.

Stade 3 · Décider

SCRATCHAPIXEL
si s <= 0 : arrière -> jetée
sinon     : avant   -> dessinée
// le test objet DÉCIDE seul ;
// le rasterizer ne revérifie pas
B5
si s < −τ : SÛREMENT arrière -> jetée,
            sans lire ses sommets
sinon     : pas assez sûr -> le test ÉCRAN
            décide, comme avant B5
            (ClassifyFaces8 : aire raster
             puis boîte serrée)

Pourquoi des rôles différents. Chez Scratchapixel, le test objet est la référence. Chez nous, la référence reste l'aire à l'écran, verrouillée par la TNR et mesurée par les compteurs ; B5 n'est qu'un raccourci devant elle. Il ne doit donc jamais contredire l'écran, ce qui exige deux choses. D'abord la même convention de signe dans tous les cas : E la donne par construction, aire_raster = −K·(L·E)/(w0·w1·w2) (étape 2b). Ensuite une marge τ : une face presque rasante a une aire float qui n'est que du bruit d'arrondi, B5 lui laisse la décision.

Stade 4 · B5 seulement : par lots de 8, en AVX2

diffuser E.x, E.y, E.z, E.w et −τ dans 5 registres      // UNE fois, hors de la boucle
pour chaque lot de 8 faces consécutives :
    s[0..7]  = 4 lectures contiguës (nx, ny, nz, d), 4 mul, 3 add
    objBack  = valid & movemask( s < −τ )               // NaN -> 0 : un doute ne rejette jamais
    si objBack == valid : lot suivant                   // ni gather de sommets, ni test écran
    m        = ClassifyFaces8(...)                      // lot mixte ou avant : B4 inchangé
    keep     = valid & ~objBack                         // une face rejetée l'est dans TOUS les cas
    front    = m.front & keep ; survive = m.survive & keep

C'est ici que se fait le gain : un lot entièrement arrière (environ la moitié sur une sphère) ne coûte plus que 13 instructions, au lieu de 24 lectures dispersées et deux tests.

Pour être juste avec Scratchapixel. Avec ses deux corrections (une branche ortho avec une direction, et un facteur signe(det(model))), sa méthode donne exactement le même résultat que E en arithmétique exacte. Elle n'est pas fausse : elle convient à un moteur où le test objet est le seul test. Dans le nôtre, B5 doit s'accorder avec un test écran qui existe déjà. Il nous faut donc une formule qui hérite de la convention du rasterizer par construction, et non par une liste de corrections qu'on pourrait oublier un jour.
